## [Unreleased]

### Security

- **Collector: rate limit on OTLP trace ingest; future-dated security events no longer outlive retention** (#373): `POST /ingest/otel/v1/traces` now has its own per-tenant limit, `PS_OTEL_TRACES_RATE_LIMIT_PER_MINUTE` (default 600 requests/minute, `0` turns it off; tenant override `ingest_rate_limits.otel_traces`), through the shared Redis/in-memory limiter and counted apart from `/ingest/events`; past it the route answers `429` with `Retry-After` (documented in `docs/openapi.yaml`, which now describes the route). Gateway security events whose `@timestamp` is more than 5 minutes ahead of arrival are stored with arrival time + 5 minutes (the sent value kept in `attributes["ps.original_timestamp"]`), and the retention purge now also deletes rows that arrived before the cutoff, so rows already stored with a future time are purged too. Chart 0.4.18 documents the new setting (may be re-bumped at merge).
- **Collector: race-free last-owner check; owner tokens out of reach of non-owners** (#372): the check that refuses removing, demoting, disabling or deleting a tenant's last enabled owner (409) read the owner count without a lock, so two concurrent demotions of two different owners could both pass and leave the tenant with no owner. Every route that can drop an owner (`PATCH`/`DELETE /api/v1/admin/memberships/{id}`, `PATCH /api/v1/admin/principals/{id}` with `disabled: true`, `DELETE /api/v1/admin/principals/{id}`) now takes a per-tenant transaction advisory lock before reading the rows it changes and holds it through the write, so those changes are serialised per tenant (`rbac_admin.lock_owners`). `DELETE /api/v1/admin/tokens/{id}` no longer lets any `admin:tokens` holder revoke any token: revoking another token needs every scope it holds, and an owner (an owner's token, or an unbound token holding every admin scope) when the token is issued for a tenant-wide owner or is unbound and holds every admin scope, so an admin can no longer cut the owner off. A token may always revoke itself, and the tokens a revoked token created still go with it; the owner check applies to each live token the cascade would revoke (also on a self-revoke), so an admin cannot revoke an owner's token by revoking the non-owner token that created it (`details.cascade_blocked_by` names it). `DELETE /api/v1/admin/partner-credentials/{id}` likewise needs an owner for a credential issued for an owner (403, audited as `partner_credential.revoke` failure, `owner_required`). Refusals are 403 and audited as `admin_token.revoke` with outcome `failure` and `details.reason` `scope_not_held` or `owner_required`. Admin tokens have no rotate route, so nothing changes there. No migration.
- **Collector: private-network opt-ins no longer reach loopback, link-local or cloud metadata** (#370): `allow_private_network` on the Partner API source of the LeanIX and ServiceNow connectors (`partner_api`) and `PS_WEBHOOK_ALLOW_PRIVATE_DESTINATIONS` (partner webhooks) admitted every non-global address, so a configured URL could reach the collector's own host or the cloud metadata service. They now admit internal networks (RFC 1918, ULA, CGNAT) only: loopback (`127.0.0.0/8`, `::1`), link-local (`169.254.0.0/16` including `169.254.169.254`, `fe80::/10`) and the cloud metadata addresses `fd00:ec2::254` and `100.100.100.200` stay refused, including IPv4-mapped, NAT64 (well-known and local-use `64:ff9b:1::/48`), IPv4-translated (`::ffff:0:0/96`), 6to4, Teredo and IPv4-compatible IPv6 forms and DNS names resolving to them (redirects were already never followed). IPv4-translated addresses embedding a non-public IPv4 address are now refused on every outbound path, opt-in or not. `collector.egress` gains the `allow_local` option (as in the SIEM connectors). **Upgrade note:** a development setup that delivered webhooks to a receiver on the collector's own host with `PS_WEBHOOK_ALLOW_PRIVATE_DESTINATIONS` must also set the new `PS_WEBHOOK_ALLOW_LOOPBACK_DESTINATIONS=true` (default `false`, development only; admits `127.0.0.0/8` and `::1`, never link-local or metadata). A Partner API source on loopback is no longer possible; point it at the collector's cluster address. Chart 0.4.17 documents the new setting (may be re-bumped at merge). No migration.

- **Collector: operator tokens bounded by the caller's own token** (#364): a named operator token holding `operator:tokens` could issue or rotate a token that outlived it (no expiry, or a later one), and revoke a token holding scopes it lacks. A token it issues or rotates now expires no later than itself: an omitted or later `expires_at` is capped to the caller's own, as tenant admin tokens already were (the audit row sets `details.expiry_capped`). Rotating can therefore shorten the target token's expiry. The same cap applies to a tenant admin token bootstrapped with `POST /api/v1/operator/tenants/{id}/admin-tokens` (its `admin_token.create` audit row sets `details.expiry_capped`). Revoke now needs every scope of the target, like rotate and issue (403 otherwise). Refused issue, rotate and revoke attempts are audited as `operator_token.issue|rotate|revoke` with outcome `failure` and `details.reason` `scope_not_held`. `PS_ADMIN_TOKEN` (break-glass) and named tokens without an expiry are not bounded. No migration.

- **Gateway: PII redacted in the `/log/stream` admin live tail** (#337): request and response bodies in the console's log stream had PII in them; only credentials and headers were redacted. Every string in a log entry now goes through the gateway's PII detector, and each email address, card number, phone number, SSN, IP address, IBAN and Nordic national ID is replaced by its category (`[EMAIL]`, `[CREDIT_CARD]`, `[PHONE]`, `[SSN]`, `[IP_ADDRESS]`, `[IBAN]`, `[NATIONAL_ID]`). A card number sent as a JSON number is replaced too, and so is PII in object keys and in the request path and query (percent-encoded or not). The response is redacted before the 100 KB truncation, so a truncated entry never shows part of a value. Redaction is always on, with no switch to turn it off. Nothing is scanned when no admin is connected to the stream. The detector gains `findPiiSpans` / `redactPii` (`gateway/src/middlewares/router/pii.ts`), which use the same patterns and checksums as `detectPiiCategories`. FORK_NOTICE.md item 58 (may be renumbered at merge).

### Added

- **Collector: principals, teams, projects and built-in roles (RBAC)** (refs #338): new tenant tables `principals` (user or service account; `external_id`, `email`, `display_name`, `disabled_at`), `teams`, `projects` (in a team) and `memberships` (a principal's role tenant-wide, in a team, or in a project; one per place), migration `039` with row-level security policies and erasure. Built-in roles `owner`, `admin`, `developer`, `viewer`, `auditor` and `billing` are named sets of existing admin and partner scopes (`collector/rbac.py`; enforcement still goes through `require_admin` / `require_scope`): a viewer reads only (`admin:read` plus partner read scopes, so every write route is 403), an auditor holds `audit:read` only. Admin CRUD under `/api/v1/admin/principals`, `/teams`, `/projects`, `/memberships` and `GET /roles` with the new admin scope `admin:members`; partner reads `GET /partner/v1/teams` and `/projects` with the new scope `members:read` (partner-ts `client.teams.list()`, `client.projects.list({ teamId })`). `POST /api/v1/admin/tokens` and `POST /api/v1/admin/partner-credentials` take an optional `principal_id`: the credential keeps the requested scopes the principal's tenant-wide roles grant, and on every request (and in every OAuth token) reaches no more than those roles grant then, so demoting, disabling or deleting the principal takes effect at once (deleting also revokes them). Only tenant-wide memberships grant scopes on today's tenant-wide routes. Granting a role needs every admin scope it carries; granting, changing or removing `owner` needs an owner, and the last enabled owner cannot be removed, demoted, disabled or deleted (409). Disabling, enabling or changing the `external_id` of a principal needs what granting its roles would, and only an owner may issue an admin token holding every admin scope that is unbound or issued for an owner (otherwise an admin could mint one and make itself owner). `principal_id` must name a principal of the caller's tenant (checked explicitly, not only by RLS). Every change writes a hash-chained `audit_events` row (`principal.*`, `team.*`, `project.*`, `membership.add`, `membership.remove`, `role.change`) with ids and roles, never emails or names. Tokens and partner credentials issued without a principal work unchanged. OpenAPI: `principal_id` on `AdminToken` and `PartnerCredential` (additive); the `AdminScope` enum gains `admin:members`, which oasdiff reports as a response enum value added (clients that switch on admin scopes should accept unknown values). Migration `039` follows `042` (ids out of order: `040` and `042` merged first); like `038` did for `admin:privacy`, it grants `admin:members` to admin tokens that held every earlier admin scope, so full-admin tokens stay full admin.

- **Collector: Splunk HEC, syslog/CEF and webhook SIEM connectors, and gateway security events in the collector** (refs #353): `PS_SIEM_EXPORT` (operator environment, per tenant) configures a Splunk HTTP Event Collector, a syslog receiver (RFC 5424 over TLS with RFC 5425 framing, ArcSight CEF or JSON) and/or an HTTPS webhook (body signed with `Prompt-Shields-Signature` when a `signing_secret` is set, optional bearer token). Each pushes per-call routing evidence and the audit trail (the Sentinel record mapping) and gateway security events (the gateway's v1 fields) from per-connector cursors that move only past accepted batches; run with `POST /api/v1/admin/connectors/{splunk-hec,syslog,webhook}/sync` (`operator:integrations`, status at `.../status`) or `python -m collector.siem_export --all-tenants`. HTTP goes through the connector SSRF guard (`GuardedClient`: https, public addresses only, DNS pinned, no redirects, bounded retries); syslog uses the same address check and verified TLS; `allow_private_network` opts in to an internal SIEM (loopback, link-local and cloud metadata addresses stay refused). Credentials are never logged, stored or returned (status shows hosts and options, not the webhook path). New table `gateway_security_events` (migration `042`, chained from `040`; may be re-chained at merge), with row-level security, stores the gateway's security events from `POST /ingest/otel/v1/logs` (the gateway's `PS_SECURITY_EVENTS_OTLP` exporter pointed at the collector with a tenant ingest key) and `POST /ingest/security-events` (forwarded NDJSON lines), validated, deduplicated by `event.id`, tenant taken from the key (scope `ingest:write`), with their own per-tenant rate limit `PS_SECURITY_EVENTS_RATE_LIMIT_PER_MINUTE` (default 600 requests/minute; tenant override `ingest_rate_limits.security_events`); read with `GET /partner/v1/security-events` (new partner scope `security-events:read`, never granted by default). Rows are purged with the tenant's retention period, deleted on tenant erasure, and the end-user erasure, by id or by stored hash, clears their `user_hash` (`rows_erased.gateway_security_events`). Chart 0.4.15 documents `PS_SIEM_EXPORT` and `PS_SECURITY_EVENTS_RATE_LIMIT_PER_MINUTE` (may be re-bumped at merge). Docs: [SIEM export](docs/integrations/siem.mdx).
- **Collector: usage time series, long-term rollups and a gateway cost metric** (refs #346): new `GET /partner/v1/usage/series` (`usage:read`) returns requests, tokens by type, cost, cache savings, cache hit rate and error rate per UTC `hour`, `day` or ISO `week`, optionally `group_by` `user` (the salted `user_id_hash`, never a raw id), `project` (the asset's use case), `model`, `provider`, `api_surface` or `asset`, cursor-paged and clamped to rollup retention; `GET /partner/v1/usage/series/export` (`usage:export`) returns the same as CSV or JSON Lines beside the FOCUS export. Both read new hourly and daily rollup tables (`usage_rollup_hourly`, `usage_rollup_daily`), kept `PS_USAGE_ROLLUP_RETENTION_DAYS` (default 760, about 25 months, never less than raw retention) and purged by the retention purge; they survive the raw event purge. A worker loop (`PS_USAGE_ROLLUP_INTERVAL_SECONDS`, default 30, `0` = off; or `python -m collector.usage_rollups refresh --all-tenants`) maintains them incrementally and exactly: per tenant, under its RLS context and a per-tenant advisory lock, it recomputes the hours of events ingested since its last run from the raw events, then their days from the hourly rows, committing a week of touched hours per transaction so the first-run backfill holds no long transaction, so a daily rollup equals the raw events to the token for days still in raw retention. `python -m collector.usage_rollups rebuild` recomputes every bucket still in raw retention. Asset merges repoint the rollups; erasure by end user (`/api/v1/admin/users/erase`) nulls the user's `user_id_hash` in them too (`rows_erased.usage_rollups`); tenant erasure deletes them. Migration `040` (chained from `038`) adds `ai_usage_events.ingested_at` (database time of insert) with an index, the two rollup tables and `usage_rollup_state`, all with the tenant isolation policy. Gateway: new `ps_gateway_cost_usd_total{provider,model,team}` counter, the estimated cost each call's telemetry event reports (`team` is `none` until principals ship), and the traffic dashboard's Cost row now charts cost by provider, model and team and cache savings (chart 0.4.14). TypeScript Partner SDK: `client.usage.series()` and `client.usage.seriesExport()`. Not done: `group_by=team` (needs principals, #338).
- **Collector: erasure by end user and a tenant audit trail read API** (refs #353, #85): `POST /api/v1/admin/users/erase` (`{"user_id": "<as sent>"}`, in the body so it never reaches an access log) and `DELETE /api/v1/admin/users/{user_id_hash}/data` erase one end user's identifiers in the caller's tenant. The collector hashes the id with the tenant's salt (#334; the salt is read, never created or rotated). On the user's `ai_usage_events`, `user_id_hash`, `user_id_raw`, `session_id` and `prompt_hash` become null while usage, cost and routing metadata stay; `call_feedback.user_id` equal to the id becomes null; `mcp_tool_usage` rows for it are merged into the no-user row of the same tool. Synchronous, batched, idempotent (a repeat reports zeros), RLS-scoped, and counts only the caller's tenant rows, so the answer says nothing about other tenants. Every call is a `user.erase` row on the tenant's hash-chained audit trail (target: the salted hash; details: per-table counts) and in `retention_audit_log` (`erase_user`). New admin scope `admin:privacy` (a new value in the `AdminScope` enum returned by `/api/v1/admin/token-scopes` and the admin token responses: api-breaking for clients that reject unknown enum values). Migration `038` grants it to every admin token that held all seven earlier scopes, so tokens that were full admin can still issue and rotate ingest keys while `PS_ADMIN_REQUIRE_SCOPED_TOKENS` is off; narrower tokens are unchanged. `GET /partner/v1/audit` (`audit:read`) lists the tenant's audit trail as JSON pages in chain order with `since`/`until`/`action` filters and the chain hashes; partner SDK `client.audit.list()` / `listPage()`. With no salt yet, an erasure by raw id matches `user_id_raw` directly and still creates no salt.
- **Collector: scoped ingest keys and named operator tokens** (#341). Ingest keys now carry scopes: `ingest:write` (event ingest), `registry:read` (`/api/v1/registry` reads and `/telemetry/loss`) and `registry:attest` (attestations); a request outside a key's scopes gets 403 and an `auth.failure` (`insufficient_scope`) on the tenant's audit chain. Migration 037 gives every existing key all three, so nothing breaks on upgrade; a key issued from now on (`POST /api/v1/admin/api-keys`, or the first key of `POST /api/v1/operator/tenants`) holds `ingest:write` only unless `scopes` / `api_key_scopes` asks for more, and only a key holding all three can call `/api/v1/admin`. Issuing or rotating a narrowed key needs only `admin:keys`. Named operator tokens (`ps-ot-...`, table `operator_tokens`: name, scopes, expiry, `created_by`) are issued, listed, rotated and revoked through `/api/v1/operator/tokens` with seven `operator:*` scopes, each operator route declaring one (`x-operator-scope` in the spec); every action is attributed to the token's name in the audit trail (actor `operator_token`), and issue/rotate/revoke are `operator_token.*` rows. `PS_ADMIN_TOKEN` stays as break-glass with every scope, and every use is now an `operator.break_glass` row on the system chain (calls to the provider usage and connector routes were `operator.access`; that name now means a named token). Named tokens keep working with `PS_ADMIN_TOKEN` unset. **Upgrade note:** the first ingest key that `POST /api/v1/operator/tenants` returns now holds `ingest:write` only: it can send events but gets 403 on the registry, attestations and every `/api/v1/admin` route (before, it could call all of them). Scripts that create a tenant or an ingest key and then use that new key for more than ingest must ask for more scopes (`"api_key_scopes": ["ingest:write", "registry:read", "registry:attest"]`, or `scopes` on `POST /api/v1/admin/api-keys`), or bootstrap an admin token for `/api/v1/admin`. Keys that already exist are not affected. `PS_ADMIN_REQUIRE_SCOPED_TOKENS` is unchanged.
- **Collector: shared rate limits in Redis and per-tenant ingest limits** (#345): with `PS_COLLECTOR_REDIS_URL` set, the Partner API limiter (tiers and custom limits) and the `/ingest/events`, `/ingest/kong`, `/ingest/mcp` and `/ingest/feedback` limiters count in Redis (atomic INCR + EXPIRE per hashed key and minute), so every uvicorn worker and replica shares one limit: a 120 rpm tier admits 120 requests a minute in total, not 120 per process. Without it the limiters stay per process, as before. If Redis errors or exceeds `PS_COLLECTOR_REDIS_TIMEOUT_SECONDS` (default 0.5) a request is counted per process instead (fail open; Redis is then skipped for 5 s so an outage does not add the timeout to every request), logged once a minute and counted in the new `ps_collector_rate_limit_store_errors` metric. Operators can override one tenant's ingest limits in `settings.ingest_rate_limits` (`events`, `kong`, `mcp`, `feedback`, `feedback_user`; 0 turns a limit off) with `PATCH /api/v1/operator/tenants/{id}`; invalid values get 400, and each process caches overrides for `PS_TENANT_LIMITS_CACHE_TTL_SECONDS` (default 30). `X-RateLimit-*` and `Retry-After` headers are unchanged. The collector now depends on `redis>=5.0`; chart version 0.4.13 documents the settings (may be re-bumped at merge).
- **Collector: gateway identity and trace fields are stored** (#334): `/ingest/events` now keeps `user_group`, `trace_id`, `retry_count`, `attempts`, `stream_truncated` and `stream_cancelled` on `ai_usage_events` instead of dropping them into `ignored_fields`, and the gateway's `route_sensitivity_level` / `route_sensitivity_source` are accepted as aliases of `sensitivity_level` / `sensitivity_source` (the canonical name wins when both are sent). `user_id` is always stored as `user_id_hash`, HMAC-SHA-256 keyed with a per-tenant salt kept in a new `tenant_secrets` table (generated on the first event with a `user_id` with `INSERT ... ON CONFLICT DO NOTHING`, never updated, so no settings write can replace it; never returned by any API; RLS-protected and erased with the tenant; the operator tenants API refuses a `user_id_salt` setting). A tenant with `settings.store_raw_user_ids: true` (boolean, default false) also gets the value as sent in `user_id_raw`. Validation is lenient like the other fields: a bad value is stored as null and counted as `<field>:invalid`; `attempts` keeps only the gateway's per-attempt metadata keys (attempt, provider, model, status, latency_ms, error_class), with provider and model limited to identifier characters so no free text is stored. Migration `035` adds the columns and `tenant_secrets`, with partial indexes on `(tenant_id, user_id_hash)` and `(tenant_id, trace_id)`; `PATCH /api/v1/operator/tenants/{id}` now locks the tenant row while merging settings. No response shape changes.
- **SDK: opt-in PII detection for person names, postal addresses and multilingual health/financial vocabulary** (refs #351): new `prompt_shields.pii_extended.detect_pii_categories_extended` (also exported from `prompt_shields`) returns what `detect_pii_categories` returns, plus `person_name` and `postal_address`. It also matches `health_data` and `financial_data` with keyword lists in sv, nb, da, fi, de, fr, nl, es, it, pl and en, and counts a checksum-valid IBAN as `financial_data`. The default backend is rule-based: pure Python, linear time, about 0.1 ms p95 per prompt. It finds names as a common given name plus a capitalised surname, a title or a cue, and addresses as a street with a house number or a UK postcode. Ambiguous words such as "recept", "Rezept", "diagnostic" and "prescrizione" are left out. `ner="spacy"` also adds a spaCy model's `PER` entities, through the new optional extra `prompt-shields[ner]` and a model such as `xx_ent_wiki_sm`. It is opt-in and default-off. `detect_pii_categories`, `find_pii_spans`, telemetry, the router, the pseudonymiser and the gateway are unchanged. The new categories are for detection and telemetry only, never for blocking, until security signs off their thresholds (#35). Benchmark: a new hand-written held-out set, `benchmarks/pii/dataset.optin.v1.jsonl` (141 examples, 11 locales), and `score.py --extended` / `--holdout`. New recall gates in `thresholds.json` (`opt_in`), set at measured recall. On the held-out set, measured before any tuning: person_name 0.69, postal_address 0.82, health_data 0.86, financial_data 0.95, with precision ≥ 0.95. On v1, which was used to build the rules: 1.00 / 1.00 / 0.95 / 1.00. Existing thresholds are unchanged. The spaCy backend was measured but is not gated: held-out name recall is 0.96, but precision is 0.81, and 0.52 on v1. Per-locale numbers and known misses are in `benchmarks/pii/README.md`. Not done: a gateway port, and wiring into client telemetry.

- **Gateway: route policy from a file** (#336): `PS_ROUTE_POLICY_FILE` names a `route-policy.v1` document (`schemas/route-policy/`). The gateway loads it before serving, checks it against the schema and the cross-field rules in its description (groups and sensitivity levels that must exist), and exits 1 with the problems listed when the file is unreadable or invalid. When set, the router is mounted with that policy (no `PS_ROUTER_ENABLED` needed), so its sensitivity stages, PII escalation and fail-closed data-policy gate run in a stock image: a call classified `confidential` to a provider the policy forbids at that level gets 403 `policy_violation` before anything is sent. The file is re-read on `SIGHUP` and, with `PS_ROUTE_POLICY_RELOAD_SECONDS`, polled; a bad reload is logged and the last good policy stays active. Spend-budget downgrades use the router's active policy. Without the variable nothing changes. Helm: `gateway.routePolicy` (rendered into a ConfigMap mounted as a directory, pods roll when it changes) and `gateway.routePolicyReloadSeconds`; chart version 0.4.12. The gateway ships a copy of the schema, kept equal to the shared one by a test.
- **SDK: `RoutedStream` finalisation** (refs #36): a `RoutedStream` / `AsyncRoutedStream` garbage-collected before it ended (never read, or left mid-way without `close()`) is now finalised once through `weakref.finalize`: its telemetry event is enqueued (not sent) and its spend recorded, the upstream opened for the first-chunk read is closed (for an async stream, scheduled on the running loop), the routing learner is told about the call (before, only the event and spend were recorded), and the pseudonymisation mapping is dropped explicitly. A stream that already ended, failed or was closed is never reported again, nothing runs at interpreter shutdown, and the finaliser never raises and logs only exception class names. Async streams keep recording spend with `commit_soon` rather than `acommit`, as the instrumented async clients do (the event can be built inside the garbage collector, where nothing can be awaited; a blocking store is still written from the executor inside a running loop, and in place, inside the collector, with no loop running in that thread, as for any instrumented client's abandoned stream); the routing guide's Limits say so. Internal: instrumented streams gain `abandon()`, the garbage-collection report made on demand.
- **Gateway: web search results in `/v1/responses` from Anthropic and Gemini** (refs #73): through the Chat Completions adapter, an Anthropic web search (`server_tool_use` + `web_search_tool_result` blocks) is now a `web_search_call` output item (`status`, `action.query`, and `action.sources` when `include` lists `web_search_call.action.sources`), and the text's `web_search_result_location` citations are `url_citation` annotations on the `output_text`. Gemini Search grounding (`groundingMetadata`) gives one `web_search_call` per search query after the message, and annotations from `groundingSupports`. Streamed responses send `response.web_search_call.in_progress` / `searching` / `completed` and `response.output_text.annotation.added`. Annotation indices count Unicode code points. Anthropic's `encrypted_content`, `encrypted_index` and cited text are never included. Native Responses targets are unchanged.
- **Cloud AI inventory: offline import for Azure and Google Cloud Vertex AI too (collector)** (refs #94): `scripts/cloud-inventory-export-azure.sh [<subscription id>...]` runs only `az ... list` commands (Cognitive Services accounts and their deployments, Machine Learning workspaces via `az resource list`, and `az ml serverless-endpoint` / `online-endpoint` / `online-deployment list`) with the operator's own `az login`, and `scripts/cloud-inventory-export-gcp.sh <project>[,...] <region>...` runs only `gcloud ai endpoints list` and `gcloud ai models list`. The live pull's Azure and Vertex AI rules are now pure functions shared by both (`azure_account_deployments`, `azure_ml_*`, `vertex_catalog_add`, `vertex_endpoint_deployments`, …), so imported assets get the same ids, model, region and tag-derived owner/environment as a pull, and an import and a later pull update the same rows. - **TypeScript Partner SDK: the OpenAPI drift test checks field types and nullability** (refs #105): besides field names and `?`, `packages/partner-ts/test/openapi.test.ts` now compares each mapped field's JSON kind (string, number (integer included), boolean, array, object) and whether it can be null with `docs/openapi.yaml`. ### Fixed

- **Collector tests: rate-limit tests no longer depend on wall-clock timing**: the failed-auth limiter (`collector/auth_cache.py`) and the fixed-window rate limiter (`collector/partner_rate_limit.py`) count in fixed 60-second windows, so a test whose requests straddled a minute boundary saw its count reset (an expected 429 became 401 or 200). `FailedAuthLimiter.clock` is now public and `FixedWindowRateLimiter` takes an optional `clock`; the failed-auth, feedback and partner rate-limiter tests pin it mid-window, and new tests show a boundary crossing resets the count. Production behaviour is unchanged.
- **Gateway: `/v1/responses` and `/v1/messages` tolerate malformed provider output** (refs #73): through the Chat Completions adapter, a provider response or stream chunk with a `null`, numeric or string entry in `choices`, `content_blocks` or `tool_calls` (or a badly typed field such as a non-string thinking text, function name or arguments) threw and became a 500; such entries are now skipped and fields type-checked, in JSON and streamed responses. Streamed tool calls are kept in a `Map` (Responses and Messages adapters), so a provider tool call `index` of `__proto__` can no longer write to `Object.prototype`. With Google Search grounding and a function call, the JSON output now lists the `web_search_call` items after the function call, as the stream does. A streamed message's last text block keeps its Anthropic web search citations when the stream ends. The Messages adapter (`/v1/messages` through Chat Completions) skips and type-checks the same entries in JSON and streamed responses, and a successful provider response whose body is not a JSON object is now a 502 `api_error` on both adapters.
- **TypeScript Partner SDK: a retried DELETE no longer surfaces a 404** (refs #105): when a DELETE is retried after a network error or 5xx and the retry gets a 404, the call now resolves as a success (`undefined`, as for any delete), since the first attempt may have deleted the resource and lost its response. A 404 on the first attempt, or after only 429s (which the server refused without acting), still throws `NotFoundError`. Applies to `providerCredentials.delete`, `providerKeyFingerprints.delete`, `webhooks.subscriptions.delete` and `client.send('DELETE', ...)`. The README and `providerKeyFingerprints.put` docs now say that `meta.corroboratedAssets` is the count from the attempt that answered, so after a retry it can be 0 although an earlier, lost attempt corroborated assets.
- **Gateway: Vertex AI token exchanges are single-flight and keyed by scope** (follow-up to #317): concurrent requests with the same service account now share one in-flight token exchange instead of each fetching a token; a failed exchange is not reused, so the next request tries again. The token cache key now also covers the OAuth scope and audience, so a token minted for one scope is never reused for another. Cached tokens from before this change miss once.
- **Gateway: one telemetry event per request for cache lookups, and an event for budget-blocked calls** (refs #33, #28): the gateway no longer sends a separate cache-only event for every cache lookup. That event had no `X-PS-*` attribution or call id (so it joined the wrong asset), counted as an extra request in `total_requests`, repeated each hit already reported on the call's event, and was sent once per failover attempt. The call's own event now carries `cache_status` for every lookup (hit, miss, bypass, refresh; not `DISABLED`) and `est_tokens_saved`, with the final response's status, so a call that falls back reports one lookup. Hits keep `cost: 0`, `cost_source: "cache"` and `cache_saved_cost`. A call refused by a spend budget now sends one event with `budget_action: "blocked"`, `budget_state: "exceeded"` (429) or `"unknown"` (503 with `on_store_error: closed`), `budget_id`, the attribution, the requested model and the call id (also returned as `X-PS-Call-Id`); no usage, cost or latency, since no provider was called. It is still not a security event. The collector's `cache_hit_rate` still counts each event with a `cache_status` as one lookup, which is right for current gateways, for released gateways (up to sdk v0.4.0, which send only the cache-only event) and for a mix during a rollout; `budget_blocked_requests` now counts the gateway's blocked events (`docs/openapi.yaml` descriptions updated, no schema change).
- **Gateway: `served_model` for providers whose response names no model** (refs #69): a routed call whose provider response carries no `model` (AI21 chat, for one) reported the router's tier model as `served_model` and priced the call at it, even when a config's `override_params.model` sent another model. - **Collector: `/docs`, `/redoc` and `/openapi.json` are off by default** — FastAPI served them without authentication, listing every route, including the operator routes such as tenant erasure. They now return 404 unless `PS_COLLECTOR_API_DOCS_ENABLED=true`, which serves them unauthenticated and logs a startup warning. `app.openapi()` still builds the schema in-process; `docs/openapi.yaml` remains the published Partner API spec.
- **Gateway: upstream redirects are not followed, and realtime upstream URLs are checked** — fetch followed a provider's 3xx, and on Node a cross-origin redirect drops only `Authorization`, so a custom host answering 307 sent the request body and the `api-key`, `x-api-key` or `x-goog-api-key` header to any `Location`, including the cloud metadata service or private hosts that the upstream URL check refuses; a provider open redirect could leak keys the same way. Every upstream call (provider requests, proxy, file and batch helpers, Entra/Vertex/OAuth token fetches, realtime) now uses `redirect: 'manual'`, and a 3xx answer is returned as a 502 `upstream_redirect` error without its `Location` and is not retried. Same-origin redirects are not followed either; no supported provider API relies on redirects. The realtime WebSocket handlers (Node and Workers) now apply the same upstream URL checks as HTTP calls (no metadata/private hosts, same origin as the provider base URL), so a crafted Azure resource name or Foundry URL can no longer open a WebSocket with the provider key to an internal host; Workers answers 400. Cohere batch output no longer sends the Cohere API key with dataset part downloads (presigned storage URLs from the Cohere response); the key goes only to the Cohere API origin, and a part URL that is not https or fails the upstream URL check is refused.
- **Gateway: the request path can no longer choose the Azure OpenAI upstream host** — a proxied Azure OpenAI request whose path contained `.openai.azure.com` was sent to `https:/<path>`, so `/v1/proxy/evil.com/.openai.azure.com/openai/deployments/x/chat/completions` delivered the target's `api-key` (or Entra token) to `evil.com`. A full Azure URL in the proxy path is now accepted only when its host is exactly the configured `<resource>.openai.azure.com` (or custom host); otherwise the request is refused with a 400 before any upstream call. Every proxied URL, for all providers, must also keep the origin of the provider's configured base URL or custom host (400 otherwise), so a future proxy URL builder bug fails closed. Non-proxy endpoints get the same check on the provider-built URL (base URL plus endpoint path, which carries model, deployment, file and batch ids), except where a provider request handler builds its own URL.
- **Gateway: guardrails apply on the proxy routes** — `/v1/proxy/*` and the `/v1/*` catch-all skipped every before/after hook and input/output/default guardrail (as upstream Portkey does), so a caller whose target had guardrails could reach the same model API through the proxy (`/v1/proxy/chat/completions` on OpenAI, `/v1/proxy/openai/v1/responses` on Bedrock Mantle) unchecked. When any target in the config has hooks or guardrails, a proxied POST whose path and JSON body are recognisably Chat Completions, Completions, Messages, Responses or Embeddings now runs the target's hooks as that endpoint type (blocking with 446, mutators rewrite the forwarded body, the Responses check allowlist applies); every other proxied request (unknown path, non-matching body, multipart, binary, GET/DELETE other than model listing) is refused with a 400 `invalid_request_error` before any upstream call — so for targets with guardrails, Assistants, file/upload, batch and other provider-native proxy paths stop working through the proxy. Mutators count as hooks, and the path is classified exactly as it is forwarded. Targets without hooks are proxied unchanged.
- **partner-ts publish job runs no dependency install scripts** (#105): `publish-partner-ts.yml` runs `npm ci --ignore-scripts`, then builds explicitly, so nothing a dependency ships runs while the job holds the id-token and `NPM_TOKEN`. A test guards the workflow. `RELEASING.md` documents protecting `partner-ts-v*` tags with a tag ruleset, a repository setting the team must enable.
- **Gateway: guardrails and mutators run on Responses API requests** (refs #73) — the hooks manager skipped every before/after hook and default guardrail for `createModelResponse`, so `/v1/responses` to OpenAI and Azure OpenAI, and `/v1/messages` for models routed to the Responses API (codex, `-pro`, deep research), reached the provider and returned to the caller without the target's input or output guardrails. Hooks now run there (as in Portkey 2.0.0): checks see the string `input` or the last input item's `input_text` parts (or `function_call_output`), as they see the last message on chat requests, and every `output_text` / `refusal` part of the output; mutators such as `regexReplace` and the PII redactors rewrite those parts (and `output_text`). A blocked request is a 446 before any upstream call, a blocked response a 446 without the model output; a failing non-deny guardrail on `/v1/messages` returns the translated response with 246 and `hook_results` (adapter responses now keep `hook_results`). Only checks verified on Responses requests may run there (an allowlist, `RESPONSES_SUPPORTED_CHECKS`); any other enabled check fails closed: a target with one is not called via the Responses API (400 `invalid_request_error`, code `unsupported_guardrail` on `/v1/responses`). **Behaviour change:** this covers `default.webhook` (the endpoint may only understand Chat Completions), custom or unknown check ids, and the checks that read only Chat Completions fields (`default.addPrefix`, `exa.online`, `lasso.classify`, `aporia.validateProject`, `azure.shieldPrompt`, `crowdstrike-aidr.guardChatCompletion`, `qualifire.toolUseQuality`); Responses requests to providers without a native Responses API go through the Chat Completions adapter and still run every check. Streaming responses are checked as on the other endpoints (after-request hooks do not inspect stream content). Also fixed: the Messages → Responses routing decision used the request's model instead of the target's `override_params.model`.
- **Gateway response cache is scoped to the caller** — the cache key was a hash of the request body and endpoint only, so with caching on, caller B could be served caller A's cached response for an identical body, and identical bodies sent to different `/v1/proxy` paths shared one entry. The key now also covers a SHA-256 digest of the provider, the caller's credential and identity fields (API key, `Authorization` and other credential headers, virtual key, Vertex service account, AWS role, Azure/OAuth client, org/project), any header the gateway forwards upstream (all non-`x-portkey-` headers on `/v1/proxy`, plus `forward_headers`; tracing headers excluded) and the full upstream URL (custom host, path and query). Raw credentials never appear in the key. Keys stay stable for the same caller, including Bedrock `assumedRole`/`serviceRole` while STS credentials rotate. Existing cache entries are unreachable after upgrade (a one-time miss).
- **Gateway: Azure host identity only goes to Azure** — with `AZURE_AMBIENT_CREDENTIALS_ENABLED=true`, `azureAuthMode` `managed` and `workload` (`azure-openai`, `azure-ai-inference`) mint a token for the gateway host's own Azure identity, and a caller could send it anywhere: a `custom_host` or `x-portkey-custom-host`, a resource name such as `evil.example#`, a non-Azure `azureFoundryUrl`, or the Azure proxy path `/v1/proxy/evil.example/x.openai.azure.com/...`. These modes now return 400 before any token request unless there is no custom host, the resource name matches `^[a-z0-9][a-z0-9-]{0,62}$`, and the Foundry URL and final upstream URL are `https`/`wss` on a Microsoft Azure AI host (`*.openai.azure.com`, `*.cognitiveservices.azure.com`, `*.services.ai.azure.com`, `*.models.ai.azure.com`, `*.inference.ai.azure.com`, their `.azure.us`/`.azure.cn` equivalents) with no port or user info. `azureEntraScope` must be the Cognitive Services audience (`https://cognitiveservices.azure.com|us|cn`, optionally `/` or `/.default`), so a caller cannot ask for, say, a `management.azure.com` or `storage.azure.com` token; the only storage token is the one the gateway itself requests to download Azure OpenAI batch output, and only that download may go to Azure Blob Storage (a proxy path such as `/v1/<account>.blob.core.windows.net/...openai.azure.com` is refused). Caller credentials (API key, `azureAdToken`, `entra` with a client secret) still work with custom hosts. Azure ML online endpoints (`*.inference.ml.azure.com`) can no longer use host identity. The Azure guardrails (`contentSafety`, `shieldPrompt`, `protectedMaterial`, `pii`) with `managed` likewise refuse a custom host or a resource name outside that pattern and fail closed; they now ask IMDS for a `https://cognitiveservices.azure.com/` token instead of passing `resourceName` as the IMDS resource.
- **Gateway cache skips multipart and binary requests** — with simple caching on, every multipart (`/v1/audio/transcriptions`, file uploads) or binary body serialised to `{}` and got the same cache key, so one audio file could get another's cached transcript. The cache now only reads and writes JSON request bodies; FormData, Blob, ArrayBuffer, typed-array and stream bodies always go to the provider (cache status `DISABLED`).
- **Collector tenant ingest keys are hashed** — tenants now store a SHA-256 lookup prefix and a bcrypt hash instead of the plaintext key in `settings`. Migration `004` hashes existing keys and removes the plaintext; downgrading cannot restore them. An unknown key and a wrong key get the same 401 after the same bcrypt work (#81).
- **Gateway admin console and log stream require auth** — `/public` and `/log/stream` now need `PS_GATEWAY_ADMIN_TOKEN` (at least 16 characters) as a bearer token or session cookie, and the log stream is disabled when it is unset. Previously anyone who could reach the gateway port could watch live request logs. Provider options and headers are redacted in the stream. Ported from upstream Portkey `main` (#54).
- **`x-portkey-forward-headers` loop guard** — requests or configs that try to forward the forward-headers header itself are rejected with 400 (upstream `de0e6c5`, #55).
- **Upstream URL SSRF check** — provider URLs built from request fields (Azure resource name, Vertex region, AWS region, account ids) may no longer point at metadata, private, link-local or alternatively encoded IPs (#65).
- **Credential masking in gateway logs** — bearer tokens, API keys, AWS and Google keys, and passwords in URLs are masked in the shared logger, the Redis connection log and error logs (#65).
- **Config fan-out cap** — at most 100 root targets (1000 for conditional routing) and 50 nested targets per root target; override with `MAX_ROOT_CONFIG_TARGETS`, `MAX_CONDITIONAL_ROOT_CONFIG_TARGETS` and `MAX_NESTED_CONFIG_TARGETS` (#65).
- **Custom-host response size cap** — responses from custom hosts are limited to 50 MiB (`PS_MAX_CUSTOM_HOST_RESPONSE_BYTES`) (#65).
- **Provider credentials win on proxy routes** — forwarded or proxied client headers no longer overwrite the credential headers a provider config sets (#65).
- **Bedrock/SageMaker cannot borrow the gateway's AWS identity** — `awsAuthType=serviceRole`, and `assumedRole` without operator-configured keys, sign with the host's credentials only when `AWS_AMBIENT_CREDENTIALS_ENABLED=true`; otherwise `serviceRole` returns 403. `assumedRole` without a role ARN returns 400 instead of signing with the operator's assume-role keys. Upstream 2.0 allows all of these for any caller (#108).
- **Azure callers cannot borrow the gateway's Azure identity** — `x-portkey-azure-auth-mode: managed` (host managed identity via IMDS) and `workload` (host federated token) on Azure OpenAI and Azure AI Inference, and `managed` credentials on the Azure guardrails, work only when `AZURE_AMBIENT_CREDENTIALS_ENABLED=true`; otherwise the request returns 403 and the guardrail fails closed (verdict `false`). Upstream allows them for any caller.
- **AWS signed requests stay on AWS** — a crafted `x-portkey-aws-region` (`x@evil.example/`) or S3 bucket name could point Bedrock, SageMaker or STS calls, and their signed headers (access key id, session token), at another host. Regions are now format-checked, signing is refused for hosts outside `AWS_ENDPOINT_DOMAIN`, and STS `RoleArn`/`ExternalId` are URL-encoded (#108).

## SDK [0.5.0] — 2026-11

### Behaviour changes when upgrading from 0.4.0

No public API is removed or renamed; `prompt_shields` exports ten new names (`AsyncRoutedStream`, `RoutedStream`, `BudgetEnforcer`, `BudgetError`, `BudgetExceeded`, `BudgetStore`, `InProcessBudgetStore`, `RedisBudgetStore`, `Pseudonymisation`, `pseudonymise`). Spend budgets, pseudonymisation and learner auto mode are off unless you pass them. These changes alter what existing callers send or see (details in the entries below):

- **`ShieldsRouter` / `AsyncShieldsRouter` (local mode) fail over by default.** After a 5xx, timeout, connection error or 429, the same request goes to the next compliant candidate, so one call can reach more than one provider (each allowed by the call's data-policy rule). A call with no compliant candidate left raises `NoCompliantCandidate` (a `PolicyViolation`, with the provider error as `__cause__`) instead of the provider SDK's error. Circuit breakers are shared per provider name across every router in the process unless you pass `breakers=` / `breaker_config=`. Pass `failover=False` to keep 0.4.0's one attempt per call.
- **Router provider entries without `base_url`:** an OpenAI-vendor entry that is not named `openai`, is not a catalogued OpenAI-compatible provider (`mistral`, `berget`, `infercom`, `regolo`, `ionos`, `stackit`, `scaleway`, `ovhcloud`) and sets no `catalog_provider` now raises `RouterError` instead of sending its key to api.openai.com. The catalogued names get their base URL from the catalog. Calls to catalogued providers are priced at the catalog's rate for that provider, not OpenAI's table, when the model id collides.
- **PII detection changes `detected_pii_types` and can change routing:** a 13-19 digit number that fails the Luhn check is no longer `credit_card`, a checksum-valid IBAN's digits are no longer also `credit_card`, and grouped IBANs and grouped `+CC` / trunk-0 phone numbers are now found. Since the router escalates sensitivity from these categories, some calls can be routed differently.
- **Pricing:** OpenAI `priority` calls on GPT-4o, GPT-4o mini, the GPT-4.1 family, o3, o4-mini, GPT-5, GPT-5 mini and GPT-5 nano now get a `cost` (they were unmetered). o4-mini flex cached input moves from $0.1375 to OpenAI's listed $0.138 / 1M. Unit and image prices now come from the catalog; their values are unchanged.
- **Learner auto mode is new in this release.** If you ran it from `main` before the release: `fetch_recommendations` no longer defaults to `http://localhost:8000`; `ps_collector_url` is required and must be `https://` (plain `http://` only to localhost), otherwise it raises `AutoModeError` before sending the partner token.
- **`ShieldsRouter` / `AsyncShieldsRouter` stream in local mode.** `stream=True` used to raise `RouterError` in local mode; it now returns a `RoutedStream` / `AsyncRoutedStream` (chunks in the serving provider's shape, not translated) and emits one telemetry event when the stream ends, fails or is closed. Failover happens only before the first chunk; an error after a chunk has been read goes to the caller and is never retried.
- **`pseudonymise=True`** (opt-in) on a client call that carries route hints or other `X-PS-*` headers raises `ValueError` and sends nothing, since the gateway does not pseudonymise.

### Behaviour changes when upgrading from 0.2.0

No public API is removed or renamed. These changes alter what existing callers send or see (details in the entries below):

- OpenAI clients now send `max_tokens` (it was silently dropped), as `max_completion_tokens` for OpenAI reasoning models. Calls that set it can now be truncated.
- Events are priced at the served model, not the requested one, so `cost` changes for routed or aliased calls.
- Anthropic `tokens_in` now includes cache reads and writes, and cache tokens are priced, so `tokens_in` and `cost` rise for prompt-cached workloads.
- MCP tool-call telemetry is batched in the background by default (`PS_MCP_TELEMETRY_MODE=sync` restores per-call sends).
- Events carry new fields (`outcome_signals`, `outcome_signals_version`, routing and usage fields); `PS_OUTCOME_SIGNALS=0` turns outcome signals off.

### Added

- **SDK: shadow-eval sampler (`prompt_shields.evals.ShadowSampler`)** (#46): samples a configurable share of served calls (`sample_rate`, default 1%), re-runs each on one alternative model allowed at the call's sensitivity, and has the pairwise judge compare it with the primary answer the user was served; the caller only ever gets the primary answer. Built on the eval harness's safety primitives: opt-in (`allow_prompt_reexecution` + `max_spend_usd` for real executors), the worst-case spend check on every alternative and judge call against both the absolute cap and `max_spend_share` of primary spend (at most 2%), the rate limiter, and an explicit per-sensitivity allowlist (`EvalPolicy.allow_all()` is refused; unknown labels count as `restricted`; `policy_from_route_policy` derives it from a `route-policy.v1` data policy). `offer()` never blocks or raises: a sampling draw and a non-blocking put on a bounded queue, with a background worker; a full queue drops and counts (`dropped_queue_full`), and `close()` drops jobs not started within its timeout (`dropped_on_close`). The validated config is snapshotted, so later changes to it have no effect; a NaN, infinite or negative cost reported by an executor is booked at the worst-case estimate (the eval harness's `SpendCap` too). `offer_routed()` is the hook for `ShieldsRouter` responses. `stats()` reports aggregates only (verdicts per use case × sensitivity × alternative, shadow spend apart from primary spend); prompts and answers are never logged or exported.
- **Failover engine and per-provider circuit breaker (SDK and gateway)** (refs #21): `prompt_shields.failover` (`FailoverEngine.run` / `arun` / `run_stream` / `arun_stream`) and the gateway's `psFailover` module implement the PRD 0001 §7.5 matrix over an ordered list of already-compliant candidates: a 429 waits `Retry-After` up to `max_wait` once, then moves on; 5xx, timeouts and connection errors move to the next candidate; a context-length error moves only to a candidate with a known, larger window; 400/401/403 and content-filter refusals raise with no fallback; a stream that emitted a chunk is never retried. The engine only removes candidates, never adds them, and `allow=` re-checks each candidate's compliance before it is called; when none is left it fails closed with `NoCompliantCandidate` (a `PolicyViolation` in the SDK). Per-provider breakers (closed / open / half-open with probe slots; configurable failure threshold, open time and probes) are per process, bounded with LRU eviction, and count transitions (`metrics()`, `on_transition`, gateway counter `ps_gateway_circuit_breaker_transitions_total{provider,to}`, registered once the module is in the request path). Results carry `attempts` and `fallback_chain` (error classes only). Both implementations pass the shared vectors in `schemas/failover/vectors.json`. Not yet wired into `ShieldsRouter` (#22) or the gateway router, which picks a single model today.
- **SDK: implicit outcome signals** (#44): every SDK event (`ShieldsClient`, `AsyncShieldsClient`, `instrument()`) gains `outcome_signals`, a sorted list of classes computed locally, and `outcome_signals_version` (`1`): `max_tokens` (truncation), `refusal` (refusal field or stop reason, content filters), `schema_invalid` (JSON `response_format` / `text.format` answer that does not parse or misses the schema's type or required keys), `tool_call_invalid` (tool-call arguments that are not a JSON object), `fallback` (non-empty `fallback_chain`), `stream_error`, `abandoned`, and `regenerate` / `retry` (the same request, or the same last user message in a `session_id`, within 120 s after a call that returned / raised). Stop reasons are read for OpenAI, Azure, Mistral, Anthropic, Gemini, Cohere, Bedrock and the Responses API, streamed or not. Only class names leave the process; the regenerate detector keeps truncated, per-process-salted SHA-256 digests in a bounded in-memory table. `PS_OUTCOME_SIGNALS=0` turns it off. The collector ignores the fields until it stores them (follow-up); meanwhile they appear under `ignored_fields` in `/telemetry/loss` and do not count as lost events.
- **SDK: `ShieldsRouter` and `AsyncShieldsRouter`, local mode (#22)**: opt-in clients that pick the model for each call under a `route-policy.v1` policy (a dict, or a `.json` / `.yaml` file) through `resolve_policy_route`: sensitivity from the declared `data_classification` (or the policy's `unclassified_default`), escalated by PII found locally in the prompt, the fail-closed data policy, the use case's quality bar, then the `RouteHint` and the budget clamp. The call goes out with your own keys (BYOK, one entry per provider in `providers`; any provider other than `anthropic` is reached through the OpenAI SDK with its `base_url`), through the existing instrumented `ShieldsClient` / `AsyncShieldsClient`. Only tiers whose provider is configured are candidates. With no allowed candidate left it raises `PolicyViolation` and sends nothing. A concrete model with no hint is pinned, but must be in the policy and allowed at the call's sensitivity. Responses are `RoutedChatCompletion` in the OpenAI chat-completions shape for every provider (Anthropic responses are translated), with the provider's own response as `raw` and `resp.ps.route` / `.cost` / `.attempts`. The telemetry event records `requested_model` (e.g. `auto`), `served_model`, `route_mode`, `route_group`, `route_reason`, `route_est_cost`, `served_provider`, `served_jurisdiction`, `policy_version` and `sensitivity_level` / `sensitivity_source`; a model missing from the pricing table is priced at the policy tier's rates (`cost_source: "route_policy"`). `mode="gateway"` delegates the decision to the gateway with the `X-PS-*` headers. The router passes every shared golden route-decision vector. Not yet: streaming in local mode, tool-call translation for Anthropic, failover (#21). The other clients are unchanged and still never pick a model.

- **SDK: cached, cache-write and reasoning token accounting** — events now carry `tokens_cached` (OpenAI `prompt_tokens_details.cached_tokens`, Anthropic `cache_read_input_tokens`, Gemini `cachedContentTokenCount`), `tokens_cache_write` (Anthropic `cache_creation_input_tokens`) and `tokens_reasoning` (OpenAI `completion_tokens_details.reasoning_tokens`, Gemini `thoughtsTokenCount`), for both plain and streamed responses. Anthropic `tokens_in` now includes cache reads and writes, matching OpenAI and the gateway. `estimate_cost` charges cache reads and writes at their own rates (vendor defaults, overridable per model), and events gain `cost_source` (`pricing_table`, or `pricing_table_estimated_tokens` when tokens were estimated). A `GeminiAdapter` parses Gemini responses but is not wired into the clients yet (#9).
- **`route-policy.v1` JSON Schema and golden decision vectors** — `schemas/route-policy/` holds the shared routing contract (JSON Schema 2020-12): groups, quality mapping, sensitivity levels, PII escalation, data policy, per-use-case quality bar and fallback. It also has three example policies and decision vectors in `vectors/*.json`. The gateway router runs every active vector through `resolveRoute`. The SDK checks the schema, the examples and `RouteHint` encoding. Sensitivity, data-policy and quality-bar vectors are marked `pending` and skipped with their reason until those P1 features land (#11).
- **SDK: telemetry for streamed calls** — `stream=True` on the sync and async clients now emits one event when the stream ends, with usage from OpenAI's final usage chunk (when the client points at api.openai.com the SDK requests `stream_options.include_usage` and hides that chunk unless you asked for it; other OpenAI-compatible hosts are left untouched, since some reject the parameter) or Anthropic's `message_start`/`message_delta`, and a ~4-chars-per-token estimate (`tokens_estimated`) otherwise. Events carry `stream_completed` (false on early close or error) and `stream_error`. Chunks pass through unchanged; telemetry failures never break the stream (#91).
- **`ps-scan` repository scanner (SDK)** — `ps-scan [PATH]` statically finds AI usage: LLM SDK imports and clients (OpenAI, Anthropic, Google GenAI, Bedrock, Mistral, Cohere, LangChain, LlamaIndex, LiteLLM), model names, provider base URLs and API-key env var names (never values) in Python, TypeScript/JavaScript, Java and Go. Prints a summary, a JSON report, collector `/ingest/events` bodies with `source="code_scan"`, or SARIF. Standard library only, no network; skips `.env*`, `.git`, `node_modules`, virtualenvs, binaries and large files (#95).
- **SDK: Nordic national-ID detection** — new `national_id` PII category for Swedish personnummer/samordningsnummer (Luhn), Norwegian fødselsnummer/D-/H-numbers (two mod-11 digits), Danish CPR (date, plus mod-11 when unhyphenated) and Finnish HETU (century marker and check character). Dates and checksums are validated to keep phone numbers, order IDs and dates out (#10).
- **Cost-aware route hints (SDK)** — `RouteHint(quality=, max_cost=, model_group=, allow_cache=)` on `chat.completions.create(route=...)` for both sync and async clients. The SDK never routes; it emits `X-PS-Quality`, `X-PS-Max-Cost`, `X-PS-Route`, and `X-PS-Cache` headers that the gateway acts on (transparent-by-default, per-route override). An empty hint emits no headers.
- **`requested_model` / `served_model` on every event** — the requested model (possibly `"auto"`) is captured alongside the model that actually ran (from the provider response / gateway `X-PS-Served-Model`), so routing savings are provable in Atlas.

### Changed

- **SDK: MCP tool call telemetry is batched off the call path** (refs #63): `call_tool` now only buffers its event (no network I/O), so a slow or unreachable collector no longer delays MCP tool calls (a 2 ms call against a 1 s collector took 1.01 s). A new `BackgroundTelemetrySender` daemon thread posts one `/ingest/mcp` request per batch, every 2 s or at 100 buffered events, and the bounded exit flush (`PS_EXIT_FLUSH_TIMEOUT`, `PS_DISABLE_EXIT_FLUSH`) sends the rest; it needs no event loop and is thread-safe. A full buffer (1,000 events) drops the oldest and counts it. While sends fail or are rate limited, it retries on the 2 s interval only, not on each new event. Batches are also split by size so a request stays under the collector's 1 MiB limit with long non-ASCII names. `instrument(mcp_telemetry_mode=...)` / `PS_MCP_TELEMETRY_MODE` = `batch` (default) or `sync` (the old per-call send). LLM telemetry is unchanged.
- **Docs: the Python SDK guide no longer says LLM responses are returned before telemetry is sent**: the event is posted after the provider responds but before the call returns, so a slow collector adds its round trip (up to 5 s); errors never fail the call.
- **ps-scan**: a test walks the scanner's tables and `Finding` sites for every vendor it can emit and checks each is in `KNOWN_VENDORS`, so a new vendor cannot be flagged as a `--fail-on` typo.
- **ps-scan: misspelled `--fail-on` tokens are reported**: a token that is not `any`, a finding kind or a known vendor is now named in a warning on stderr and ignored (it was silently ignored, so `--fail-on antropic` never failed). If none of the tokens is known, ps-scan exits 2 with a usage error before scanning, so the GitHub Action step fails instead of passing.
- **SDK: `instrument()` patches google-genai, mistralai, cohere and boto3 when they are imported** — instead of importing every installed SDK up front (about 0.9 s of startup with all of them installed), `instrument()` patches a module at once if it is already imported, and otherwise through an import hook when the app first imports it; `uninstrument()` removes the hook. Calling `instrument()` at startup and importing or creating clients afterwards works as before. openai and anthropic are still imported and patched up front, unchanged (#88, #89).
- **SDK: abandoned streams are reported** — a stream from an instrumented call that the caller leaves without reading to the end or calling `close()` (a `break` out of the loop) now emits its event when it is garbage-collected, once, with `stream_completed: false` and `stream_abandoned: true`. The event is queued, not sent, inside the garbage collector and goes out with the next flush; nothing is emitted at interpreter shutdown, and a google-genai stream dropped before its first read made no request and emits nothing. An Anthropic `messages.stream()` manager that is never entered gives back a framework call it claimed. `ShieldsClient` streams are unchanged (#88, #89).
- **SDK: stream telemetry follow-ups (exit flush, Cohere early close, `ShieldsClient` abandoned streams)** — Events still buffered when a short script exits (an abandoned stream's event, a send that failed) are now sent by one best-effort `atexit` flush, bounded by a total budget of 2 s (`instrument(exit_flush_timeout=...)` or `PS_EXIT_FLUSH_TIMEOUT`; `0` or `PS_DISABLE_EXIT_FLUSH=1` turns it off). It never raises, keeps a 429 back-off, and only covers senders registered by `instrument()` / `ShieldsClient` / `AsyncShieldsClient`; `uninstrument()` and `close()` / `aclose()` unregister them. A forked child process (a gunicorn or multiprocessing worker) starts with an empty buffer and its own client id: the events queued before the fork are sent by the parent only, not again by each child's flushes or exit flush. Leaving a Cohere `chat_stream` loop early (sync or async) is now reported as an early close (`stream_completed: false`, without `stream_abandoned`), like `close()` on an OpenAI or Anthropic stream, and its event is queued instead of sent with a blocking flush from the generator's close (which can run in the garbage collector). A raw Cohere `chat_stream` context that is never entered gives back its framework claim when collected. `ShieldsClient` and `AsyncShieldsClient` streams now also report abandoned streams (queued, `stream_abandoned: true`). The `latency_ms` of a stream that ends early without an error now runs to the last chunk read, not to the close or the garbage collection. LlamaIndex `register()` / `unregister()` keep tracking handlers they failed to remove, so a later call retries instead of leaving them attached and untracked (#88, #89).
- **SDK: Cohere clients created before `instrument()` are instrumented** — cohere's `Client` stores bound `chat` / `chat_stream` methods on each instance when it is created, so patching those missed clients built earlier. `instrument()` now patches the raw clients they call (`RawBaseCohere`, `RawV2Client` and their async versions); calls made through `with_raw_response` are reported too. Cohere versions without raw clients keep the previous behaviour (#89).
- **SDK: LlamaIndex `register()` is fail-open** — if the installed LlamaIndex's dispatcher does not accept the handlers, `register()` logs a warning, leaves nothing half-attached and returns None instead of raising; `unregister()` logs its errors too (#90).
- **SDK: Anthropic `tokens_in` now counts cached prompt tokens** — it is `input_tokens + cache_read_input_tokens + cache_creation_input_tokens`, the total prompt size, matching OpenAI `prompt_tokens`. Before, it was `input_tokens` alone, which leaves cache reads and writes out. For prompt-cached workloads, Anthropic `tokens_in` and `cost` will both rise: cache tokens used to be left out of the cost, and are now billed at the cache read and write rates. Use `tokens_cached` and `tokens_cache_write` for the split (#9).

### Fixed

- **SDK: `max_tokens` reaches OpenAI, and multi-part prompts no longer break PII scanning**: `ShieldsClient` / `AsyncShieldsClient` with `vendor="openai"` dropped the `max_tokens` argument of `chat.completions.create` instead of sending it; it is now sent, as `max_completion_tokens` for OpenAI reasoning models (`o1`, `o3-mini`, `gpt-5`, ...), which reject `max_tokens` (an explicit `max_completion_tokens` wins). `scan_messages` raised `TypeError` (after the provider call) when a message's `content` was a list of content parts; it now scans their text parts.
- **SDK: price events at the served model (#6)**: `ShieldsClient`, `AsyncShieldsClient`, `instrument()` and the framework integrations now price a call at the model that actually ran (`served_model`), not the requested one. `model="auto"` calls routed by the gateway are no longer left at `cost=None`, and a call routed from gpt-4o to gpt-4o-mini is no longer billed at gpt-4o rates. A served id without a price falls back to the requested model; OpenAI version dates (`gpt-4o-2024-08-06`) and Gemini stable versions (`gemini-1.5-pro-002`) resolve to their base price, and an explicit Azure deployment map still wins. Adapters list candidates with `ProviderAdapter.pricing_candidates()`; `pricing.resolve_pricing_model()` / `has_price()` pick the first priced one, and `pricing._lookup_rates()` is the single rate lookup a generated catalog (#7/#8) can plug into. Tests cover cached, cache-write and reasoning usage for OpenAI, Anthropic, Gemini, Azure OpenAI, Bedrock, Mistral and Cohere across plain, sync-stream and async-stream calls (#9). `StreamAccumulator("azure_openai")` now reads OpenAI-shaped chunks.
