# Authentication

The Partner API supports two authentication methods. Use whichever fits your integration.

## OAuth 2.0 Client Credentials (Primary)

Best for: Programmatic integrations, custom scripts, CI/CD pipelines.

<Steps>
  <Step title="Exchange credentials for a token">
    ```bash
    POST /oauth/token
    Content-Type: application/x-www-form-urlencoded

    grant_type=client_credentials
    &client_id=ps-partner-ardoq-abc123
    &client_secret=sk-partner-secret-xyz789
    ```
  </Step>
  <Step title="Use the access token">
    ```bash
    GET /partner/v1/assets
    Authorization: Bearer eyJhbGciOiJSUzI1NiIs...
    ```
  </Step>
  <Step title="Refresh before expiry">
    Tokens expire after **1 hour** (3600 seconds). Request a new token before the current one expires. There is no refresh token flow — simply call `/oauth/token` again.
  </Step>
</Steps>

### Token Response

| Field | Type | Description |
|-------|------|-------------|
| `access_token` | string | JWT access token |
| `token_type` | string | Always `"Bearer"` |
| `expires_in` | integer | Seconds until expiry (3600) |
| `scope` | string | Space-separated list of granted scopes |

## Partner API Key (Fallback)

Best for: Integration Builder tools (Ardoq, LeanIX) that don't support OAuth client credentials.

```bash
GET /partner/v1/assets
Authorization: Bearer ps-pk-your-key-here
```

API keys don't expire but can be revoked from the Atlas AI Dashboard.

<Warning>
  API keys have the same scopes as the credential they belong to, but they are
  long-lived bearer secrets. Use OAuth when possible.
</Warning>

## Scopes

Each credential is granted a set of scopes, and every endpoint requires one.
A request without the endpoint's scope gets `403`, whether it uses an OAuth
token or an API key. Scopes not granted are denied.

| Scope | Endpoints |
|-------|-----------|
| `assets:read` | `/assets`, `/assets/{id}`, `/vendors`, `/models`, `/business-units` |
| `data-flows:read` | `/assets/{id}/data-flows` |
| `risks:read` | `/assets/{id}/risks` |
| `usage:read` | `/assets/{id}/usage-summary` |
| `changes:read` | `/changes` |
| `export:read` | `/export` |
| `webhooks:manage` | Webhook subscriptions. Never granted unless asked for |
| `attestations:write` | `POST /assets/{id}/attestations`. Never granted unless asked for |
| `provider-credentials:manage` | `/provider-credentials`, `/provider-key-fingerprints` (provider admin keys for the org usage pull, write-only). Never granted unless asked for |

New credentials get the six read scopes unless the tenant admin picks fewer.
Changing a credential's scopes takes effect on its next request, including
requests made with OAuth tokens issued before the change: a token never grants
more than its credential currently holds.

<Info>
  **Existing credentials:** `registry:read`, the single Phase 1 scope, still
  works. It stands for the six read scopes above, so credentials and tokens
  issued with it keep the access they had. It does not include scopes added
  later, such as `webhooks:manage`.
</Info>

### Managing scopes and tiers (tenant admins)

Tenant admins manage credentials with the tenant API key:

| Method | Path | Purpose |
|--------|------|---------|
| `GET` | `/api/v1/admin/partner-scopes` | Scopes, the `registry:read` alias and rate-limit tiers |
| `POST` | `/api/v1/admin/partner-credentials` | Issue a credential: `scopes`, and either `rate_limit_tier` or a custom `rate_limit` |
| `GET` | `/api/v1/admin/partner-credentials` | List credentials with scopes, tier and effective limit |
| `PATCH` | `/api/v1/admin/partner-credentials/{id}` | Change `scopes`, `rate_limit_tier` or `rate_limit` |
| `DELETE` | `/api/v1/admin/partner-credentials/{id}` | Revoke |

```bash
curl -X PATCH https://api.promptshields.io/api/v1/admin/partner-credentials/$ID \
  -H "Authorization: Bearer $PS_API_KEY" -H "Content-Type: application/json" \
  -d '{"scopes": ["assets:read", "changes:read"], "rate_limit_tier": "premium"}'
```

Unknown scopes or tiers, or a request that sets both `rate_limit_tier` and
`rate_limit`, return `400`.

## Security Best Practices

<AccordionGroup>
  <Accordion title="Store credentials securely">
    Never hardcode `client_secret` or `api_key` in source code. Use environment variables or a secrets manager (AWS Secrets Manager, Azure Key Vault, HashiCorp Vault).
  </Accordion>
  <Accordion title="Rotate keys periodically">
    Generate new credentials from the Atlas AI Dashboard quarterly. Old keys can be revoked immediately.
  </Accordion>
  <Accordion title="Use TLS only">
    All API traffic must use HTTPS. HTTP requests are rejected.
  </Accordion>
  <Accordion title="Cache tokens">
    OAuth tokens are valid for 1 hour. Cache the token and reuse it for multiple requests instead of requesting a new token per API call.
  </Accordion>
</AccordionGroup>

## Error Responses

Authentication failures return RFC 7807 Problem Details:

```json
{
  "type": "about:blank",
  "title": "Unauthorized",
  "status": 401,
  "detail": "Invalid or expired access token"
}
```

| Status | Cause | Action |
|--------|-------|--------|
| `401` | Missing, invalid, or expired token | Re-authenticate |
| `403` | Token lacks required scope | Request token with correct scopes |
