# ServiceNow Integration

Connect Prompt Shields to ServiceNow to add AI assets to your CMDB.

<Info>
  The built-in ServiceNow connector pushes AI assets and their vendors as
  CIs, with an asset-to-vendor relationship, and optionally the systems
  their data flows connect to, with data flow relationships, and business
  units and risk mappings when enabled per tenant. It has not
  yet been verified against a live ServiceNow instance (PDI); check the
  identification rules below in a sub-production instance before using it
  in production.
</Info>

## How it works

The connector runs in the collector deployment. It reads the tenant's
registry through the **Partner API**, with a partner API key, and writes it
to the CMDB through the **Identification and Reconciliation Engine (IRE)**
REST API (`POST /api/now/identifyreconcile`):

1. First run: `GET /partner/v1/export`.
2. Later runs: `GET /partner/v1/changes?since=<cursor>`.
3. With `data_system_class` set: `GET /partner/v1/assets/{id}/data-flows`
   for each asset read.
4. Send the assets to IRE in batches (one request per batch, with the
   vendors, data flow systems and relationships of those assets).
5. Store the new cursor in the tenant settings. If IRE rejects any item or
   relationship, the run fails and the cursor stays where it was, so the
   next run retries the same changes.

### Why IRE and not the Table API

The Table API inserts rows exactly as given. A connector writing `cmdb_ci_*`
tables with it duplicates CIs that Discovery or Service Graph connectors
already own and skips the reconciliation rules that decide which source may
update which attribute. IRE identifies every item against the class's
identification rules before inserting or updating, applies reconciliation
and data refresh rules, creates relationships from the same payload and tags
each write with the data source. ServiceNow recommends IRE for any
integration that writes CIs.

### Mapping

| PS Data | CMDB | Identifier |
|---------|------|------------|
| AI Asset, SaaS / externally hosted vendor | `asset_class` CI (default `cmdb_ci_function_ai`) | `promptshields:asset:<asset id>` |
| AI Asset, self-hosted vendor | `self_hosted_asset_class` CI (default `cmdb_ci_appl_ai_application`) | `promptshields:asset:<asset id>` |
| AI Vendor | `provider_class` CI (default `cmdb_ci_service`) | `promptshields:provider:<vendor>` |
| Asset → Vendor | `cmdb_rel_ci`, type `Depends on::Used by` | |
| Data flow system (opt-in) | `data_system_class` CI | `promptshields:system:<hash>` |
| Data flow | `cmdb_rel_ci`, type `Sends data to::Receives data from` | |
| Business unit (opt-in) | `business_unit_table` record (e.g. `cmn_department`), referenced from the asset CI's `business_unit_field` (default `department`) | `name`; source native key `promptshields:business-unit:<name>` |
| Risk mapping (opt-in) | `cmdb_key_value` related entry of the asset CI | key `promptshields:risk:<framework>:<category>` |

### AI CI classes

The AI classes ship with the **CMDB CI Class Models** store application,
version **1.75.0 or later** (some sources cite 1.68.0; 1.75.0 is the release that lists `cmdb_ci_appl_ai_application`); CSDM 5 describes the same two classes:

| Class | Label | Use |
|-------|-------|-----|
| `cmdb_ci_function_ai` | AI Function | AI hosted or developed outside your organisation: the SaaS model APIs (OpenAI, Anthropic, Bedrock, Vertex AI, ...) that most Prompt Shields assets are |
| `cmdb_ci_appl_ai_application` | AI Application (extends `cmdb_ci_appl`) | AI your organisation hosts itself |

An asset goes to `self_hosted_asset_class` when its vendor (compared
case-insensitively) is in `self_hosted_vendors` (default `ollama`, `vllm`,
`llamacpp`, `localai`, `tgi`, `triton`, `self_hosted`), and to
`asset_class` otherwise. Set `self_hosted_asset_class` to `null` to send
every asset to `asset_class`. On an instance without the store application,
point both at classes you have (for example a custom `u_` class, or
`cmdb_ci_appl` with the identification rule below).

Each CI carries its identifier as `correlation_id` and as the
`source_native_key` of its `sys_object_source_info` (source name = the
configured data source). The identifiers are the AI-BOM (CycloneDX)
`bom-ref` values, so a CI can be traced to its BOM entry. Re-running a sync
updates the same CIs; the connector never deletes CIs.

| Lifecycle | `install_status` | `operational_status` |
|-----------|------------------|----------------------|
| active | 1 (Installed) | 1 (Operational) |
| stale | 1 (Installed) | 2 (Non-Operational) |
| retired | 7 (Retired) | 6 (Retired) |

`name` is the use case (or vendor and model) followed by the first eight
characters of the Prompt Shields id; `short_description` lists vendor,
model, business unit, owner, environment, region, classification,
confidence and lifecycle (and, with data flows enabled, the number of
flows and the PII types detected in them). Business units and risk
mappings are opt-in, see below.

### Data flows

Off by default. Set `data_system_class` to a CMDB class (for example
`cmdb_ci_appl` or a custom `u_` class, with the same independent
identification rule on `correlation_id` as the other classes) and give
the partner credential the `data-flows:read` scope. Each run then reads
the data flows of every asset it pushes and sends:

- one CI per external system a flow connects to, named after the system
  and identified by `promptshields:system:` plus the first 32 hex
  characters of the SHA-256 of its name (whitespace collapsed, lower
  case), since system names can be longer than `correlation_id` (100
  characters). The same system seen by several assets is one CI.
- a `Sends data to::Receives data from` relationship per direction:
  system → asset for `input` / `inbound` flows (the system is the flow's
  source), asset → system for `output` / `outbound` flows (the system is
  the destination), and both for bi-directional flows (the source is the
  system).

Flows with another direction, or whose system is empty or `unknown` (a
telemetry event with no calling service), are skipped and counted in
`data_flows_skipped`, as are systems beyond the first 100 of one asset.
Incremental runs push the flows of the assets that changed. Relationships
of flows that no longer exist are not removed.

### Business units and risk mappings (opt-in)

Both are off by default; a tenant without the fields below gets exactly
the payloads it got before.

**Business units** (`"business_unit_table": "cmn_department"`). A business
unit is not a CI, and IRE payload relationships (`cmdb_rel_ci`) cannot
point at a non-CMDB record. IRE does support a fixed set of non-CMDB tables
in the global scope, Department (`cmn_department`) among them, and links
records with `referenceItems`. So each distinct business unit (whitespace
collapsed, at most 100 characters) is sent once per request as a
`cmn_department` item with only `name` set, and every asset in that
business unit gets a reference entry that fills its CI's `department`
field (a `cmdb_ci` base field). Because only `name` is sent, an existing
department with the same name is linked, not changed. CSDM's
`business_unit` table is not on IRE's global non-CMDB list; point
`cmn_department.business_unit` at it inside ServiceNow if you use it. Set
`business_unit_field` for another reference field (for example a custom
`u_` field on your AI classes pointing at a custom table).

**Risk mappings** (`"push_risk_mappings": true`). The connector reads each
asset's **confirmed** risk mappings (`GET /partner/v1/assets/{id}/risks`;
rule suggestions are never pushed) and sends them in the asset CI's
`related` array as `cmdb_key_value` entries: key
`promptshields:risk:<framework>:<category>` (framework `custom` when
unset; hashed when longer than 100 characters), value the highest level
(`critical`, `high`, `medium`, `low`), the same as the AI-BOM
`risk:<framework>:<category>` properties. IRE writes related entries under
a Related Entry rule and does not use them to identify the CI.

Why not GRC / IRM risk records: `sn_risk_risk`, `sn_risk_definition` and
the compliance tables belong to the Integrated Risk Management
application, are not CMDB classes IRE identifies, and need IRM's own APIs
and licence. Key values on the CI are available on every instance, and IRM
can pick the CIs up as entities (an entity filter on the AI classes, or on
their `promptshields:risk:*` key values).

Limitations: the connector never deletes, so a risk mapping that is later
rejected or removed keeps its key value until you remove it (run a full
sync after a review round to refresh the levels). Incremental runs only
see assets that changed; a risk review alone does not change the asset,
so it reaches ServiceNow on the asset's next change or the next full sync.

## Setup

1. In ServiceNow:
   - Install or update **CMDB CI Class Models** (ServiceNow Store) to
     1.75.0 or later, so `cmdb_ci_function_ai` and
     `cmdb_ci_appl_ai_application` exist; or set `asset_class` /
     `self_hosted_asset_class` to classes you already have.
   - Give each class the connector writes (`cmdb_ci_function_ai`,
     `cmdb_ci_appl_ai_application` and the vendor class, `cmdb_ci_service`
     by default) an **independent identification rule with one identifier
     entry on `correlation_id`** (CI Class Manager → class → Identification
     Rule → Add identifier entry, criterion attribute `correlation_id`,
     independent). This is required: the connector sends no hosting CI, and
     `cmdb_ci_appl_ai_application` inherits the `cmdb_ci_appl` rule, which
     is dependent (it needs a "Runs on" host), so IRE would otherwise answer
     `MISSING_DEPENDENCY` or `MISSING_MATCHING_ATTRIBUTES` and the run
     fails. Check the rules in a sub-production instance first; the class
     definitions above come from the store application release, and
     out-of-the-box identifier entries can differ between versions.
   - Business units (opt-in): enable IRE for non-CMDB tables if your
     release needs it, and create an identification rule (CI Identifier
     with an identifier entry on `name`) for `cmn_department` in the list
     views (CI Class Manager does not manage non-CMDB tables).
   - Risk mappings (opt-in): add a **Related Entry** rule
     (`cmdb_related_entry`) for `cmdb_key_value` on each asset class, with
     the referenced field `configuration_item` and `key` as the matching
     attribute.
   - Add a choice `PromptShields` (or your `data_source`) to the
     `cmdb_ci.discovery_source` choice list and, if other sources write the
     same classes, a reconciliation rule for it.
   - Create an integration user with the `itil` and `import_transformer`
     roles (or a narrower role allowed to call the IRE API on those classes),
     or an OAuth application registry entry with the client credentials
     grant enabled for that user.
2. In Prompt Shields, issue a partner credential for the connector with the
   scopes `export:read` and `changes:read`, plus `data-flows:read` if
   you push data flows and `risks:read` if you push risk mappings
   (`POST /api/v1/admin/partner-credentials`).
3. Configure the connector in the collector's environment, per tenant:

```bash
PS_SERVICENOW='{
  "<tenant uuid>": {
    "instance_host": "acme.service-now.com",
    "oauth_client_id": "<client id>",
    "oauth_client_secret": "<client secret>",
    "partner_api": {
      "base_url": "https://collector.example.com",
      "api_key": "<partner API key>"
    }
  }
}'
```

Use `"username"` and `"password"` instead of the OAuth fields for basic
auth; exactly one of the two is required. Optional per-tenant fields:
`data_source` (default `PromptShields`), `asset_class` (default
`cmdb_ci_function_ai`), `self_hosted_asset_class` (default
`cmdb_ci_appl_ai_application`; `null` to use `asset_class` for every
asset), `self_hosted_vendors` (JSON list, see above), `provider_class`
(default `cmdb_ci_service`;
`null` pushes assets only, without vendor CIs or relationships) and
`batch_size` (assets per IRE request, default 50, at most 100; a request
also closes early once it reaches 500 CIs) and `data_system_class`
(default `null`, see [Data flows](#data-flows)), `business_unit_table`
(default `null`: off; e.g. `cmn_department`), `business_unit_field`
(default `department`) and `push_risk_mappings` (default `false`; see
[Business units and risk mappings](#business-units-and-risk-mappings-opt-in)).
For a
collector reached over an internal network, set
`"allow_private_network": true` under `partner_api`; it must still be https.

### Security

- The OAuth client secret, the password and the partner API key live only
  in the operator environment. They are never stored in the database,
  logged or returned by any endpoint. Error messages carry status codes and
  IRE error codes, never response bodies or IRE error messages.
- The partner API key must belong to the tenant it is configured under.
  Every Partner API response names the key's tenant (`meta.tenant_id`); if
  it is not the configured tenant, or missing, the run fails before
  anything is written to ServiceNow and the cursor does not move.
- `instance_host` must be a DNS name ending in one of
  `PS_SERVICENOW_ALLOWED_HOST_SUFFIXES` (JSON list, default
  `[".service-now.com"]`). Calls go only to `https://<instance_host>`, the
  host must resolve to public addresses, the connection goes to the checked
  address, and redirects are never followed.
- Every Partner API read made by the connector is checked against the
  credential's scopes and recorded in the partner audit log.
- With OAuth, the access token is fetched once per run and fetched again
  shortly before its `expires_in` runs out (60 seconds before, or a tenth
  of its lifetime if shorter). If a call still answers `401`, the token is
  fetched again and the call repeated once; a second `401` fails the run.
  Tokens are never logged.
- Requests time out after 30 seconds; `429`, `5xx` and network errors are
  retried up to four times, honouring `Retry-After`.

## Running a sync

```bash
# Operator API (Authorization: Bearer $PS_ADMIN_TOKEN)
curl -X POST https://collector.example.com/api/v1/admin/connectors/servicenow/sync \
  -H "Authorization: Bearer $PS_ADMIN_TOKEN" \
  -d '{"tenant_id": "<tenant uuid>"}'          # add "full": true to ignore the cursor

curl "https://collector.example.com/api/v1/admin/connectors/servicenow/status?tenant_id=<tenant uuid>" \
  -H "Authorization: Bearer $PS_ADMIN_TOKEN"

# CLI
python -m collector.servicenow --tenant <tenant uuid> [--full]
```

Both run as the target tenant, so they work with row-level security
enforced. Schedule the CLI (for example every 4 hours) with your job
runner; the collector has no built-in scheduler yet.

## Do it yourself

You can also pull from the Partner API with a scheduled IntegrationHub flow
(REST step `GET /partner/v1/changes?since={last_sync}`, then a CMDB step)
and map the data yourself. Authenticate with OAuth 2.0 client credentials
(`POST /oauth/token`) or a partner API key, and write CIs through IRE as
above.
