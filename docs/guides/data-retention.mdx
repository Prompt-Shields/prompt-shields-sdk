# Data Retention and Erasure

Raw usage events (`ai_usage_events`) can include session ids and prompt hashes, so the collector keeps them for a limited time. Assets in the registry, with their first-seen and last-seen dates, are kept. Purging old events does not remove an asset.

MCP tool usage (`mcp_tool_usage`: per server and tool call counts, first and last seen) follows the same retention period: the purge deletes rows not seen since the cutoff, since they only summarise calls older than it. The purge result reports them as `mcp_tool_usage_deleted`.

## Retention period

Each tenant keeps usage events for `retention_days` days:

| Source | Setting |
|--------|---------|
| Default for all tenants | `PS_RETENTION_DAYS_DEFAULT` (default `365`) |
| Per-tenant override | `tenants.settings.retention_days`, set through the operator API below |

Valid values are 1 to 36500. A missing or invalid override falls back to the default, so a bad setting can never widen what gets deleted.

Events with a `timestamp` older than `now - retention_days` are eligible for purge. Code that reads events can clamp its window to the same cutoff:

```python
from collector.retention import retention_cutoff, get_retention_cutoff

start = max(start, retention_cutoff(tenant))           # with a Tenant or its settings dict
cutoff = await get_retention_cutoff(db, tenant_id)     # looks the tenant up; None if absent
```

The Partner API `usage-summary` endpoint already does this, so a `90d` summary for a tenant with 30-day retention covers only the last 30 days, even before the purge has run.

## Running the purge

Nothing is deleted until the purge runs. The collector has no built-in scheduler. The Helm chart (0.4.11 and later) runs it daily as the `retentionPurge` CronJob (`37 2 * * *`), **on by default**: after an upgrade from an earlier chart, its first run deletes everything already past each tenant's retention window (see "Upgrading" in the chart README; set `cronJobs.jobs.retentionPurge.enabled: false` to opt out). Elsewhere, run it from cron or a Kubernetes CronJob:

```bash
python -m collector.retention purge                 # every tenant
python -m collector.retention purge --tenant <id>   # one tenant
python -m collector.retention purge --dry-run       # count only
```

The purge deletes in batches of `PS_RETENTION_BATCH_SIZE` rows (default `5000`) and commits after each batch, so it never holds a long lock on `ai_usage_events`. It is idempotent: a second run deletes nothing. Each run that deletes rows writes one `retention_audit_log` row per tenant with the cutoff and the count.

<Warning>
The first purge after upgrading deletes every event older than the default 365 days. Run it with `--dry-run` first, and set per-tenant overrides before that if any tenant needs longer.
</Warning>

## Operator API

These endpoints act across tenants, so a tenant API key cannot call them. Set `PS_ADMIN_TOKEN` and send `Authorization: Bearer $PS_ADMIN_TOKEN`. Without `PS_ADMIN_TOKEN` the endpoints return 404.

| Method | Path | Purpose |
|--------|------|---------|
| `POST` | `/api/v1/operator/retention/purge` | Purge. Body: `{"tenant_id": "<optional>", "dry_run": false}` |
| `GET` | `/api/v1/operator/tenants/{tenant_id}/retention` | Show retention days and the current cutoff |
| `PUT` | `/api/v1/operator/tenants/{tenant_id}/retention` | Set the override. Body: `{"retention_days": 90}`, or `null` to clear it |
| `DELETE` | `/api/v1/operator/tenants/{tenant_id}?confirm={tenant_id}` | Erase the tenant |

## Erasing a tenant

`DELETE /api/v1/operator/tenants/{tenant_id}` removes everything the tenant owns: usage events, data flows, risk mappings, partner audit log, partner credentials, assets, MCP tool usage, and finally the tenant row. The `confirm` query parameter must repeat the tenant id.

Erasure runs in batches, child tables first. If it stops part-way, run it again: it is idempotent and reports `tenant_existed: false` once the tenant row is gone. Every erasure is recorded in `retention_audit_log` with per-table counts. That table has no foreign key to `tenants`, so the record survives the erasure. It stores counts only, never the deleted data.

Every delete is filtered on `tenant_id`. The tests check that purging or erasing one tenant leaves every other tenant's rows untouched, and that any new table with a `tenant_id` column is included in erasure.

## User ids

Usage events can carry a `user_id`: the gateway's OIDC subject (see [Gateway OIDC](/guides/gateway-oidc)) or the SDK's `ps_metadata.user_id`. The collector does not store it as sent unless the tenant asks for that:

- `user_id_hash` is always stored: HMAC-SHA-256 of the value, keyed with a salt per tenant. It is the key for per-user usage and erasure by user. The collector generates the salt on the first event that carries a `user_id` and keeps it in its own `tenant_secrets` table, written once and never changed (settings updates cannot touch it). No API, export or log returns it, and the operator tenants API refuses a `user_id_salt` setting. Without the salt a hash cannot be matched to a guessed user id, and one user's hashes differ between tenants. Erasing the tenant deletes the salt.
- A tenant whose settings have `store_raw_user_ids: true` (set with `PATCH /api/v1/operator/tenants/{tenant_id}`, `{"settings": {"store_raw_user_ids": true}}`; a boolean, default `false`) also gets the value as sent in `user_id_raw`, next to the hash. Only enable it when you need the identifiers themselves, for example to answer an access request by user name.

The setting applies to events ingested afterwards; stored events are not rewritten. Events also keep `user_group`, `trace_id`, `retry_count`, `attempts` (per-attempt provider, model, status, latency and error class, never content) and the `stream_truncated` / `stream_cancelled` flags.

## Erasing one end user

A tenant erases what the collector holds about one of its end users with the tenant admin API (admin token scope `admin:privacy`, or the tenant API key while `PS_ADMIN_REQUIRE_SCOPED_TOKENS` is off):

| Method | Path | Body | Reaches |
|--------|------|------|---------|
| `POST` | `/api/v1/admin/users/erase` | `{"user_id": "<id as the gateway or SDK sent it>"}` | usage events, call feedback, MCP tool usage |
| `DELETE` | `/api/v1/admin/users/{user_id_hash}/data` | none | usage events |

Send the raw id in the POST body, not in a URL, so it never lands in an access log. The collector hashes it with the tenant's salt; it never creates or rotates the salt for an erasure. Admin tokens that held every admin scope before `admin:privacy` existed are given it by migration `038`.

What changes, in the caller's tenant only:

- **Usage events** of the user (matched by `user_id_hash`; an event with `user_id_raw` always has the hash too): `user_id_hash`, `user_id_raw`, `session_id` and `prompt_hash` (a SHA-256 of the prompt text) are set to null. Model, tokens, cost and routing metadata stay, so spend reports do not change; the rows no longer say whose they were.
- **Call feedback** with `user_id` equal to the id as sent: `user_id` is set to null. The score stays.
- **MCP tool usage** rows for the id: merged into the row for the same tool with no user, so the counts stay.

Call feedback and MCP usage store the id as the gateway sent it, so only the POST form reaches them.

The response gives the user's salted hash (`user_id_hash`, null if the tenant never stored a user id), per-table counts in `rows_erased` and the audit row's id. The erasure runs immediately, in batches. It is idempotent: a repeat reports zeros. Every request, including a repeat, writes a `user.erase` row to the tenant's [audit trail](/guides/audit-trail) (target: the salted hash, details: the counts) and an `erase_user` row to `retention_audit_log`. Counts only ever cover the caller's tenant, so the answer does not reveal whether another tenant has seen the same id.

Events that arrive after the erasure are stored as usual, so stop sending the id first. Copies already sent elsewhere (webhook receivers, Microsoft Sentinel or another SIEM) are outside the collector: erase them there.
