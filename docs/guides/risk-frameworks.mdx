# Risk Frameworks

Each AI asset can be mapped to one or more governance frameworks with a risk category and risk level.

## Supported Frameworks

| Framework | Description |
|-----------|-------------|
| `NIST_AI_RMF` | NIST AI Risk Management Framework |
| `ISO_42001` | ISO/IEC 42001 AI Management System |
| `EU_AI_ACT` | European Union AI Act |
| `custom` | Organization-specific framework |

## Risk Categories

| Category | Description |
|----------|-------------|
| `strategic` | Risk to business strategy or competitive position |
| `operational` | Risk to day-to-day operations or service delivery |
| `compliance` | Risk of regulatory non-compliance |
| `cyber` | Risk of data breach or security incident |
| `reputational` | Risk to brand or public trust |

## Risk Levels

| Level | Meaning |
|-------|---------|
| `critical` | Immediate action required |
| `high` | Action required within defined SLA |
| `medium` | Monitor and plan remediation |
| `low` | Acceptable risk, periodic review |

## Example

An AI asset using GPT-4o for interview screening with candidate PII:

```json
{
  "data": [
    {
      "risk_category": "compliance",
      "risk_level": "high",
      "framework": "EU_AI_ACT"
    },
    {
      "risk_category": "operational",
      "risk_level": "medium",
      "framework": "NIST_AI_RMF"
    },
    {
      "risk_category": "reputational",
      "risk_level": "high",
      "framework": "ISO_42001"
    }
  ]
}
```

## Suggested Classifications

The collector can suggest mappings from what it already knows about an asset.
Suggestions are not determinations: each one is stored with
`status: "suggested"` until someone confirms or rejects it.

**Signals.** Registry fields (use case, business unit, calling service,
vendor, model, environment) and the data flows derived from telemetry: input
data sources, output destinations, detected PII categories and the highest
data classification seen.

**Rules are data.** Each JSON file in `packages/collector/collector/risk_rules/`
is a versioned ruleset:

| Ruleset | Frameworks | Covers |
|---------|------------|--------|
| `eu_ai_act_annex_iii` | `EU_AI_ACT` | The eight Annex III high-risk areas (biometrics, critical infrastructure, education, employment, essential services, law enforcement, migration and border control, justice and democratic processes), one rule per point or sub-point |
| `data_protection` | `NIST_AI_RMF`, `ISO_42001` | Personal and sensitive PII, restricted data (NIST privacy-enhanced and secure-and-resilient; ISO/IEC 42001 Annex A.7 data and A.5 impact assessment) |

A rule fires when its `when` conditions match and no `unless` condition does
(for example, Annex III point 5(b) credit scoring excludes fraud detection).
Conditions match keywords against signals (whole words, or word prefixes with
a trailing `*`), PII categories (`any_of`, `present`) or a minimum data
classification (`at_least`). `supporting` conditions add evidence and raise
confidence: `low` when only weak triggers matched (a business unit name, for
instance), `high` when supporting evidence matched too, otherwise `medium`.

The engine does not assess the Article 6(3) derogation or whether a system is
placed on the EU market; a reviewer decides that.

**Explainability.** Every suggestion carries `rule_id`, `ruleset_version`,
`framework_ref` (for example `Annex III, point 4(a)`), `confidence` and
`evidence`, which lists each signal that matched, the value and the keyword or
PII category it matched, plus a one-line `summary`:

```json
{
  "risk_category": "employment",
  "risk_level": "high",
  "framework": "EU_AI_ACT",
  "status": "suggested",
  "source": "rules",
  "rule_id": "eu_ai_act.annex_iii.4a.recruitment",
  "ruleset_version": "1.0.0",
  "framework_ref": "Annex III, point 4(a)",
  "confidence": "high",
  "evidence": {
    "summary": "Annex III, point 4(a), Recruitment or selection: ...: use_case 'resume-screening' matched resume* (trigger); data_sources 'ats_api' matched ats (trigger); pii_types 'email, national_id' matched national_id (supporting)",
    "signals": [
      {"signal": "use_case", "value": "resume-screening", "matched": ["resume*"], "role": "trigger"},
      {"signal": "data_sources", "value": "ats_api", "matched": ["ats"], "role": "trigger"},
      {"signal": "pii_types", "value": ["email", "national_id"], "matched": ["national_id"], "role": "supporting"}
    ]
  }
}
```

**Running it.** Per tenant, with the tenant API key:
`POST /api/v1/admin/risk-suggestions/run`, or for one or all tenants
`python -m collector.risk_suggestions --tenant <id>` / `--all-tenants`. Runs
are idempotent.

**Reviewing.** `POST /api/v1/admin/risk-mappings/{risk_id}/review` with
`{"status": "confirmed"}` or `{"status": "rejected"}`. The engine only creates,
refreshes or withdraws rows that are still `suggested`: it never changes a
confirmed or rejected row, never re-suggests a reviewed rule, and does not
suggest a framework and category that already has a hand-entered mapping on
the asset. Suggestions whose rule stops firing are withdrawn.

**Reading.** `GET /api/v1/registry/assets/{id}/risks` and
`GET /partner/v1/assets/{id}/risks` return every mapping except rejected ones,
each with `status` and `source`; pass `?status=suggested|confirmed|rejected`
to filter. The CycloneDX export lists unconfirmed suggestions as
`promptshields:risk-suggestion:<framework>:<category>` properties, separate
from `promptshields:risk:*`, and leaves rejected ones out.

## How Risks Map to Ardoq

In Ardoq's metamodel, each risk mapping becomes a **Risk component** linked to the AI Use Case via a `has_risk` reference. This allows CISOs to filter the Ardoq landscape by risk level or framework. Integrations that should only carry reviewed classifications can request `?status=confirmed`.
