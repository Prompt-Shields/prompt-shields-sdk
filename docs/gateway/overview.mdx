# AI Gateway API

The gateway's HTTP API is described in
[`docs/gateway-openapi.yaml`](https://github.com/Prompt-Shields/prompt-shields-sdk/blob/main/docs/gateway-openapi.yaml)
(OpenAPI 3.1). It covers every route the gateway mounts: Chat Completions,
Completions, Responses, Messages, Embeddings, Rerank, Images, Audio, OCR,
Files, Batches, Fine-tuning, Models, Realtime, the `/v1/{path}` proxy
catch-all, `/v1/health` and `/metrics`. A gateway test fails when a route is
added to or removed from the gateway without the spec.

Request and response bodies are a minimal subset: the fields the gateway
reads or translates. Every other field passes through to the provider; the
upstream OpenAI, Anthropic and Cohere specifications describe them in full.

## Authentication

The gateway does not authenticate clients. `Authorization: Bearer <key>` (or
`x-api-key`) carries the **provider's** key and is forwarded to the provider;
credentials can also be set in `x-portkey-config`. Put the gateway behind an
API gateway such as Kong for client authentication. `/v1/health` is public,
and `/metrics` needs `PS_METRICS_TOKEN` as a bearer token when that is set.

## Headers

| Header | Purpose | Sent to the provider? |
|--------|---------|-----------------------|
| `x-portkey-provider` / `x-portkey-config` | Target provider, or a full config (targets, retries, fallbacks, guardrails). One is required. | Never |
| `x-portkey-custom-host`, `-forward-headers`, `-request-timeout`, `-trace-id`, `-metadata`, `-strict-open-ai-compliance`, `-default-input-guardrails`, `-default-output-guardrails`, `-messages-via-responses` | Per-request gateway options | Never |
| `x-ps-route`, `x-ps-quality`, `x-ps-max-cost` | Cost-aware routing hints (`PS_ROUTER_ENABLED=true`) | Never |
| `x-ps-cache` | `on`, `off` or `refresh` | Never |
| `x-ps-business-unit`, `x-ps-use-case`, `x-ps-owner`, `x-ps-data-classification`, `x-ps-environment` | Business context for telemetry, OTel spans and metrics labels | Never |
| `x-ps-call-id` | Your id for the call (1-128 of `A-Za-z0-9._:-`; the Python SDK sends one), kept as the telemetry event's `call_id`. Without one the gateway makes a UUID. Either way it comes back in the `x-ps-call-id` response header (when telemetry is on, `PS_API_KEY`) | Never |

Headers named in `x-portkey-forward-headers` are forwarded on every route, except `x-ps-*` headers, which the gateway never sends upstream.
Provider credential headers (`x-portkey-aws-secret-access-key`,
`x-portkey-vertex-service-account-json` and similar) are accepted but are
deliberately not part of the spec.

## Call Feedback

`POST /v1/feedback` records how good a call's answer was, naming the call by
its `x-ps-call-id`: `{"call_id": "...", "score": 0.0-1.0 or true/false,
"reason": "incomplete", "user_id": "..."}`. Metadata only: `reason` is one
of a fixed set of labels and there is no field for free text. The gateway
forwards it to the collector with `PS_API_KEY` (503 without it). It is
rate-limited per user and per replica (`PS_FEEDBACK_RATE_LIMIT_PER_MINUTE`,
default 60, `0` turns it off): the OIDC subject with `PS_OIDC_ENABLED` (whose
pseudonym is also the `user_id` forwarded), else the caller's credential
header, else one shared anonymous bucket.

## Errors

| Status | When | Body |
|--------|------|------|
| 400 | Missing or invalid provider, config, custom host or content type | `{"status": "failure", "message": ...}` |
| 400 | Guardrails are configured and a proxied request cannot be inspected (fail closed, before any upstream call) | `error.code: "unsupported_guardrail"` |
| 408 | `x-portkey-request-timeout` exceeded | OpenAI-shaped `error` |
| 411 | `MAX_FILE_PAYLOAD_SIZE_IN_MB` set and a multipart upload has no `content-length` | `{"status": "failure", ...}` |
| 413 | `content-length` over `MAX_JSON_PAYLOAD_SIZE_IN_MB` (JSON) or `MAX_FILE_PAYLOAD_SIZE_IN_MB` (multipart uploads) | `{"status": "failure", ...}` |
| 246 | Success, but a non-denying guardrail failed | Normal body plus `hook_results` |
| 446 | A guardrail with `deny: true` failed | `error.type: "hooks_failed"` plus `hook_results` |
| 502 | The provider answered with a redirect, which the gateway never follows | `error.type: "upstream_redirect"` |
| other | Provider errors, passed through | OpenAI-shaped `error` |

## Import into Kong

[decK](https://developer.konghq.com/deck/file/openapi2kong/) turns the spec
into Kong services and routes, one route per `operationId`:

```bash
deck file openapi2kong --spec docs/gateway-openapi.yaml --output-file kong-gateway.yaml
# The generated service points at the spec's server (http://localhost:8787):
# change its host to your gateway, add plugins, then:
deck gateway sync kong-gateway.yaml
```

Things to set on the Kong side:

- **Client authentication.** Add your auth plugin (OIDC, key-auth) to the
  generated service; the spec's security schemes describe provider keys, not
  Kong credentials.
- **Strip credential headers** if clients must not bring their own provider
  credentials, for example with `request-transformer`:

  ```yaml
  plugins:
    - name: request-transformer
      config:
        remove:
          headers:
            - x-portkey-config
            - x-portkey-custom-host
            - x-portkey-aws-access-key-id
            - x-portkey-aws-secret-access-key
            - x-portkey-aws-session-token
            - x-portkey-azure-ad-token
            - x-portkey-azure-entra-client-secret
            - x-portkey-vertex-service-account-json
  ```

  Removing `x-portkey-config` means the gateway's provider comes from
  `x-portkey-provider` (or a header Kong injects).
- **Proxy catch-all.** `openapi2kong` turns `/v1/{path}` into a route that
  matches a single path segment. If clients use multi-segment provider paths
  through the proxy, add a prefix route for `/v1/` by hand.
- **Streaming.** Chat, Messages and Responses stream server-sent events;
  disable response buffering on those routes.
