# Change Webhooks

Instead of polling [`/partner/v1/changes`](/api-reference/sync/get-changes), a partner integration can receive a signed HTTPS `POST` when an asset in the tenant's registry changes.

## Events

| Type | Sent when |
|------|-----------|
| `asset.created` | A new AI asset is discovered (SDK, gateway or OTel telemetry) |
| `asset.changed` | An asset's discovery sources, confidence, owner, data classification or lifecycle state changes. This includes going `stale` and being reactivated. `data.changed_fields` names the fields that changed. |
| `asset.retired` | The lifecycle sweep retires an asset |
| `asset.attested` | Someone records an attestation (`POST …/assets/{id}/attestations`) for one of the asset's fields (attested, disputed, retired or reset to unreviewed). `data.attestation` says which field and state. |

Body:

```json
{
  "id": "6f1c2d1e-8a8e-4b4e-9d4f-1d2a3b4c5d6e",
  "type": "asset.changed",
  "created_at": "2026-10-15T09:12:44.120391+00:00",
  "tenant_id": "0b7d…",
  "data": {
    "asset": {
      "id": "3c9e…",
      "vendor": "openai",
      "model": "gpt-4o",
      "use_case_name": "resume-screening",
      "business_unit": "HR",
      "environment": "production",
      "status": "active",
      "data_classification": "confidential",
      "discovery_source": ["sdk", "gateway"],
      "confidence": "verified",
      "lifecycle_state": "active",
      "first_seen": "2026-09-01T10:00:00+00:00",
      "last_seen": "2026-10-15T09:12:44+00:00",
      "lifecycle_changed_at": null
    },
    "changed_fields": ["confidence", "discovery_source"]
  }
}
```

`asset.attested` carries the same asset summary plus:

```json
"attestation": {
  "id": "0192…",
  "field": "owner",
  "state": "disputed",
  "actor_type": "tenant",
  "attested_at": "2026-10-15T09:20:01.554120+00:00"
}
```

Payloads hold an asset summary only. They never include the owner's email address, prompt content or usage events. Attestation events leave out who attested (`attested_by`, usually an email address), the comment (free text) and the attested value (for `owner`, an email address); read them from `GET /partner/v1/assets/{id}/attestations` (`assets:read`). To get the full asset, call [`GET /partner/v1/assets/{id}`](/api-reference/assets/get-asset).

Headers:

| Header | Value |
|--------|-------|
| `Prompt-Shields-Signature` | `t=<unix seconds>,v1=<hex HMAC-SHA256>`. During a secret rotation's grace period there is one `v1` per valid secret: `t=…,v1=<new>,v1=<old>` |
| `Prompt-Shields-Event-Id` | The event `id`. It stays the same across retries, so use it to drop duplicates. |
| `Prompt-Shields-Event-Type` | The event `type` |
| `Prompt-Shields-Delivery-Attempt` | `1` for the first try, then `2`, `3` and so on |

## Verifying signatures

`v1` is `HMAC-SHA256(secret, "<t>." + raw_body)`, written as hex. Before you parse the JSON:

1. Recompute the HMAC over the **raw** request body.
2. Compare it in constant time with **every** `v1` value in the header, and accept the request if any one matches. There are two `v1` values while a rotated-out secret is still in its grace period (see [Rotating the secret](#rotating-the-secret)).
3. Reject the request if `t` is more than 5 minutes from your clock. This stops a captured request from being replayed later.
4. Treat a header you cannot parse (no `t`, a `t` that is not a number, no `v1`, non-ASCII characters) as a failed check, not an error.

Python:

```python
import hashlib
import hmac
import time

TOLERANCE_SECONDS = 300


def verify_prompt_shields_signature(secret: str, raw_body: bytes, header: str) -> bool:
    """True if the header carries a valid signature. Never raises on a bad header."""
    if not isinstance(header, str):
        return False
    timestamp, signatures = None, []
    for item in header.split(","):
        key, sep, value = item.partition("=")
        if not sep:
            continue  # not "key=value": ignore it
        if key == "t" and timestamp is None:
            timestamp = value
        elif key == "v1":
            signatures.append(value)
    if (
        timestamp is None
        or not signatures
        or not (timestamp.isascii() and timestamp.isdigit())
        or len(timestamp) > 12
    ):
        return False
    t = int(timestamp)
    if abs(time.time() - t) > TOLERANCE_SECONDS:
        return False
    expected = hmac.new(
        secret.encode(), f"{t}.".encode() + raw_body, hashlib.sha256
    ).hexdigest()
    # One v1 per valid secret during a rotation: accept any match. Check
    # every value so the time taken does not show which one matched.
    matched = False
    for v in signatures:
        matched |= v.isascii() and hmac.compare_digest(expected, v)
    return matched


# Flask example
# @app.post("/prompt-shields")
# def receive():
#     if not verify_prompt_shields_signature(
#         SECRET, request.get_data(), request.headers.get("Prompt-Shields-Signature", "")
#     ):
#         abort(400)
#     event = request.get_json()
#     ...
```

Node.js:

```javascript
import crypto from "node:crypto";

// Returns true if the header carries a valid signature. Never throws on a bad header.
export function verifyPromptShieldsSignature(secret, rawBody, header, toleranceSeconds = 300) {
  if (typeof header !== "string") return false;
  let t;
  const signatures = [];
  for (const item of header.split(",")) {
    const i = item.indexOf("=");
    if (i < 0) continue; // not "key=value": ignore it
    const key = item.slice(0, i);
    const value = item.slice(i + 1);
    if (key === "t" && t === undefined) t = value;
    else if (key === "v1") signatures.push(value);
  }
  if (t === undefined || signatures.length === 0 || !/^[0-9]{1,12}$/.test(t)) return false;
  const timestamp = Number(t);
  if (Math.abs(Date.now() / 1000 - timestamp) > toleranceSeconds) return false;
  const expected = Buffer.from(
    crypto
      .createHmac("sha256", secret)
      .update(`${timestamp}.`)
      .update(rawBody) // Buffer of the raw body, not re-serialized JSON
      .digest("hex"),
  );
  // One v1 per valid secret during a rotation: accept any match.
  let matched = false;
  for (const v of signatures) {
    const b = Buffer.from(v);
    if (b.length === expected.length && crypto.timingSafeEqual(expected, b)) matched = true;
  }
  return matched;
}
```

Reply with any `2xx` status within 10 seconds. Do slow work after you respond.

## Retries and dead letters

A delivery fails when the response is not `2xx`, including redirects (redirects are not followed), or when the connection fails or times out. Failed deliveries are retried after 1 minute, 5 minutes, 30 minutes, 2 hours, 6 hours, 12 hours, and then every 24 hours. After `PS_WEBHOOK_MAX_ATTEMPTS` attempts (default 8, about a day and a half in total), the delivery is marked `dead`.

Events can arrive out of order, and an event can arrive more than once. Use `Prompt-Shields-Event-Id` to drop duplicates, and compare `created_at` or re-read the asset when order matters.

If the partner credential is revoked or expired, or no longer has the scope for the event (`changes:read` for asset events), its subscriptions stop receiving events. Queued deliveries are moved to `dead` and are not sent.

## Managing subscriptions (tenant admin)

The tenant manages subscriptions with its own API key, not with partner credentials, because the tenant decides where its registry data is sent. The partner credential must be active and have the `changes:read` scope, which asset events need because they carry the same data as the [changes feed](/api-reference/sync/get-changes). Phase 1 credentials with `registry:read` already include it. A credential with only `assets:read` cannot be subscribed.

```bash
curl -X POST https://collector.example.com/api/v1/admin/webhooks/subscriptions \
  -H "Authorization: Bearer $PS_API_KEY" -H "Content-Type: application/json" \
  -d '{"partner_id": "<partner credential id>",
       "url": "https://ea-tool.example.com/hooks/prompt-shields",
       "event_types": ["asset.created", "asset.changed", "asset.retired"]}'
```

The response includes `secret` (`whsec_…`). This is the only time it is shown, so give it to the partner over a secure channel.

### Rotating the secret

`POST /subscriptions/{id}/rotate-secret` issues a new secret and returns it once. By default the old secret stops working at once. To switch the receiver over without dropping deliveries, send a grace period of up to 7 days (604800 seconds):

```bash
curl -X POST https://collector.example.com/api/v1/admin/webhooks/subscriptions/$SUB_ID/rotate-secret \
  -H "Authorization: Bearer $PS_API_KEY" -H "Content-Type: application/json" \
  -d '{"grace_period_seconds": 86400}'
```

Until `rotation_grace_ends_at` (shown on the subscription), every delivery carries two signatures, `t=…,v1=<new secret>,v1=<old secret>`. A receiver that checks every `v1` (as in the samples above) accepts requests with either secret, so it can be given the new secret at any point in the window. After the window only the new secret signs, and the collector deletes the old one within the hour (the worker's hourly cleanup, or `python -m collector.webhooks purge`), even for a subscription with no deliveries. Rotating again ends any earlier grace period; only the secret being replaced is kept.

### Changing or pausing a subscription

`PATCH /subscriptions/{id}` changes any of `url`, `event_types` and `is_active`. Fields you leave out keep their value. An empty body, `null` values and unknown fields are refused (`422`).

```bash
# Pause
curl -X PATCH https://collector.example.com/api/v1/admin/webhooks/subscriptions/$SUB_ID \
  -H "Authorization: Bearer $PS_API_KEY" -H "Content-Type: application/json" \
  -d '{"is_active": false}'

# Move to a new endpoint and narrow the events
curl -X PATCH https://collector.example.com/api/v1/admin/webhooks/subscriptions/$SUB_ID \
  -H "Authorization: Bearer $PS_API_KEY" -H "Content-Type: application/json" \
  -d '{"url": "https://ea-tool.example.com/hooks/v2", "event_types": ["asset.retired"]}'
```

- A new `url` gets the same checks as on creation (see [Endpoint rules](#endpoint-rules)). Queued deliveries go to the new URL.
- New `event_types` must be known event types, and the partner credential must be active and hold the scope for each (`changes:read`). The same check applies when you resume a paused subscription. Pausing always works, even for a revoked credential.
- While paused, no events are queued for the subscription, and deliveries already queued are moved to `dead` ("subscription disabled") instead of being sent. After you resume, redeliver them from the dead-letter view, and read [`/partner/v1/changes`](/api-reference/sync/get-changes) to catch up on changes made during the pause.
- The response is the updated subscription (never the secret). Every call is written to the audit log with the names of the fields that changed, not their values.

| Method and path (under `/api/v1/admin/webhooks`) | |
|---|---|
| `POST /subscriptions` | Create a subscription. Returns the secret once. |
| `GET /subscriptions[?partner_id=]` | List subscriptions (secrets are never returned) |
| `GET /subscriptions/{id}` | Get one subscription |
| `PATCH /subscriptions/{id}` | Change `url`, `event_types` or `is_active` (pause or resume). See [Changing or pausing a subscription](#changing-or-pausing-a-subscription). |
| `DELETE /subscriptions/{id}` | Delete a subscription and its deliveries |
| `POST /subscriptions/{id}/rotate-secret` | Issue a new secret. Returns it once. Optional body `{"grace_period_seconds": n}` keeps the old one signing for up to 7 days. |
| `GET /deliveries?status=dead\|pending\|succeeded` | Dead-letter view (the default) and the other statuses |
| `POST /deliveries/{id}/redeliver` | Queue a dead or succeeded delivery again |

### Endpoint rules

- The URL must use `https`, must not contain credentials or a fragment, and can be at most 2048 characters.
- Every address the host name resolves to must be public. Loopback, private, link-local (including cloud metadata `169.254.169.254`), carrier-grade NAT, multicast, deprecated IPv6 ranges (IPv4-compatible `::/96`, site-local `fec0::/10`) and IPv4-mapped, 6to4, Teredo and NAT64 (`64:ff9b::/96`) forms of these are refused. This is checked when the subscription is created and again on every delivery. The request goes to the address that was checked, and TLS is verified against the host name.
- A partner credential can have at most 10 subscriptions.

## Operating the collector

| Setting | Default | |
|---|---|---|
| `PS_WEBHOOK_SECRET_KEYS` | (empty) | Keyring that encrypts signing secrets at rest (AES-GCM): `kid:key,kid:key,…`. The first key encrypts; every listed key decrypts what it encrypted. Key ids are 1–32 characters from `A-Z a-z 0-9 _ -`; keys are at least 32 characters, for example `openssl rand -base64 32`, and cannot contain commas. See [Rotating the encryption key](#rotating-the-encryption-key). |
| `PS_WEBHOOK_SECRET_KEY` | (empty) | The single legacy key. It encrypts while `PS_WEBHOOK_SECRET_KEYS` is empty, and always decrypts secrets stored without a key id (written before the keyring). With neither set, webhooks are off. |
| `PS_WEBHOOK_WORKER_INTERVAL_SECONDS` | `0` | When above 0, each collector process runs the delivery loop in the background. Otherwise, run `python -m collector.webhooks deliver --loop` as its own worker. Workers claim rows with `SKIP LOCKED`, so several can run at the same time. |
| `PS_WEBHOOK_MAX_ATTEMPTS` | `8` | Attempts before a delivery is marked `dead` |
| `PS_WEBHOOK_TIMEOUT_SECONDS` | `10` | Overall deadline for each attempt (resolve, connect, send, response headers). Above 0 and at most 60, so attempts fit inside the worker's 5-minute claim lease; the collector refuses to start otherwise |
| `PS_WEBHOOK_DELIVERY_RETENTION_DAYS` | `30` | `succeeded` and `dead` rows older than this are deleted (by the worker once an hour, or by `python -m collector.webhooks purge`). The same run deletes rotated-out secrets whose grace period is over. |
| `PS_WEBHOOK_ALLOW_HTTP`, `PS_WEBHOOK_ALLOW_PRIVATE_DESTINATIONS` | `false` | For local development only |

Events are written to the `webhook_deliveries` outbox in the same transaction as the change that caused them. Ingest requests never wait on partner endpoints.

### Rotating the encryption key

Stored secrets record the id of the key that encrypted them, so the encryption key can change without re-issuing every subscription secret. The first key in `PS_WEBHOOK_SECRET_KEYS` is the active one, and every process re-encrypts secrets with its active key as it uses them. So every process must have a key before any process makes it active. With more than one collector process or worker, roll a new key out in two restarts:

1. **Add the new key after the active one, everywhere** (`2026a:<old>,2026b:<new>`) and restart every collector process and worker. Nothing is encrypted with the new key yet, and every process can now read it.
2. **Make it active, everywhere**: move it to the front (`2026b:<new>,2026a:<old>`) and restart again. Processes that have not restarted yet keep encrypting with the old key, which every process can still read.
3. Secrets are re-encrypted with the new key as deliveries use them. To do all of them now, run `python -m collector.webhooks rekey` once every process has the new order. It prints `checked`, `rekeyed`, `unchanged` and `unreadable` counts.
4. When a run reports `unreadable: 0` and nothing left to rekey, remove the old key (and `PS_WEBHOOK_SECRET_KEY`) from every process and restart.

On the first move from the single `PS_WEBHOOK_SECRET_KEY` to a keyring, keep `PS_WEBHOOK_SECRET_KEY` set when you add the keyring. The first keyring key is active at once (there is no step 1), so processes that have not restarted yet cannot read secrets that restarted ones have re-encrypted. Their deliveries are retried as described below, so finish the restart well within the retry window, or stop the workers while you switch.

If a process finds a secret encrypted with a key it does not have (a restart still in progress, or step 1 skipped), it does not send that delivery. It logs one warning per key id, counts the attempt and retries with the normal backoff, with `last_error` "signing secret uses key id … not configured on this worker; will retry". A process that has the key delivers it on a later attempt. Only after `PS_WEBHOOK_MAX_ATTEMPTS` attempts does the delivery go `dead`; put the key back and redeliver it.

A secret that a configured key cannot decrypt (corrupted, or not written for that subscription) is marked `dead` at once with "signing secret unreadable; rotate the secret". Rotate that subscription's secret.
